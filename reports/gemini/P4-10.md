## Corrections (Round 1 Fix)

### 1. Response Body Limit Sizing under HTML Escaping (SEC-060)
- **Root Cause**: The coordinator's `writeJSON` (`internal/api/handlers.go`) uses `json.NewEncoder` with default settings, which has HTML escaping enabled (`SetEscapeHTML(true)`). A legal task payload of `executor.MaxPayloadSizeBytes` (64 KiB = 65,536 bytes) consisting of characters like `<`, `>`, or `&` is re-encoded into 6-byte Unicode escape sequences (`\u003c`, `\u003e`, `\u0026`). On the wire, this expands the payload up to ~384 KiB. The initial 128 KiB limit (`executor.MaxPayloadSizeBytes + 64*1024` = 131,072 bytes) would reject this legal job with `unexpected EOF`, causing the job to burn through retry attempts.
- **Fix**: Sized `MaxPollResponseBytes = 6*executor.MaxPayloadSizeBytes + 64*1024` (448 KiB / 458,752 bytes) in `internal/worker/client.go`, with an inline comment explaining that the 6x factor accounts for encoder HTML escaping of up to 64 KiB payloads, plus 64 KiB headroom for the JSON envelope, identifiers, and lease metadata.
- **New Test**: Added `TestPollWork_MaxLegalAssignmentEscapedAccepted` in `internal/worker/hardening_test.go`. The test constructs a 64 KiB JSON string payload of `<`, encodes it via `json.NewEncoder` with default HTML escaping (>393 KiB body, verified > 5*MaxPayloadSizeBytes to prevent vacuous testing), and asserts that `pollWork` accepts and decodes the payload completely and intact.
  - Initial run against 128 KiB limit: Failed with `unexpected EOF` (red).
  - Run after fix (458,752 bytes limit): Passed cleanly (green).
  - Existing oversized response tests (`TestPollWork_OversizedResponseRejected`) still pass against the new limit.
- **Mutation M5**: Reverted constant `MaxPollResponseBytes` to single-multiplier baseline (`executor.MaxPayloadSizeBytes + 64*1024`). Killed by `TestPollWork_MaxLegalAssignmentEscapedAccepted` (unexpected EOF). Evidence recorded in `docs/agents/handoffs/P4-10-evidence/M5.txt`.

### 2. Null Assignment Handling on HTTP 200 (Scope Addition)
- **Base Code Behavior**: In `origin/main:internal/worker/client.go` func `pollWork`, an HTTP 200 response with null assignment (`{"assignment": null}` or `{}`) was decoded into `res.Assignment` as nil, returning `(*coordinator.WorkAssignment(nil), nil)`. Downstream in func `(a *Agent) Run`, the polling loop checked `if assignment == nil { time.Sleep(baseBackoff); continue }`, which reset `consecutiveFailures` to 0 and silently slept `baseBackoff` before retrying.
- **Hardening Rule**: P4-10 adds an explicit check in func `pollWork`: `if res.Assignment == nil { return nil, errors.New("poll returned 200 OK without an assignment") }`. An HTTP 200 response lacking an assignment is an invalid coordinator protocol response (empty queue returns HTTP 204 No Content). Downstream in func `Run`, returning an error triggers failure handling (`consecutiveFailures++`, warning log `"work poll error"`, and exponential backoff with jitter).
- **New Test**: Added `TestPollWork_NullAssignmentRejected` in `internal/worker/hardening_test.go`, verifying that HTTP 200 with `{"assignment": null}` produces the expected error.
- **Mutation M6**: Removed the `res.Assignment == nil` check in func `pollWork`. Killed by `TestPollWork_NullAssignmentRejected` (expected error on 200 OK with null assignment, got nil). Evidence recorded in `docs/agents/handoffs/P4-10-evidence/M6.txt`.
