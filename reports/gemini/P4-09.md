# Slice P4-09 Final Report: SEC-012 Worker Execution Timeout Clamp

## 1. Problem & Architecture Review

Under finding **SEC-012**, the worker in `internal/worker/client.go` converted the assignment's `TimeoutSeconds` field directly to a `time.Duration` with no upper bound:
```go
execCtx, cancel := context.WithTimeout(ctx, time.Duration(assignment.TimeoutSeconds)*time.Second)
```
While the coordinator enforces a valid range of `[1, 86400]` seconds on job submission (SEC-014), in V1/V2 before mutual authentication and TLS are introduced (SEC-004), a network attacker or compromised coordinator could return an arbitrary multi-year timeout, holding worker execution slots indefinitely. Furthermore, on 64-bit systems, large values exceeding $9.22 \times 10^9$ seconds cause 64-bit integer multiplication overflow when converting to nanoseconds, producing negative durations.

Slice P4-09 resolves SEC-012 by:
1. Referencing the coordinator's existing maximum execution timeout bound (`coordinator.MaxTimeoutSeconds = 86400`) via a shared constant `MaxExecutionTimeoutSeconds` in `internal/worker/client.go` without duplicating literal values.
2. Implementing the pure function `ClampExecutionTimeout(timeoutSeconds int) time.Duration` that clamps upper values to 86400 s (24 h), clamps non-positive values up to 1 s, guards against 64-bit integer multiplication overflow, and logs a structured warning (`slog.Warn`) with numeric-only fields.
3. Conducting an exhaustive audit of all coordinator-supplied values used in the worker, fixing SEC-012, and registering three new findings (**SEC-059**, **SEC-060**, and **SEC-061**) for remaining coordinator boundary gaps.

## 3. Summary of Changes

### `internal/worker`
- `internal/worker/client.go`:
  - Defined `MaxExecutionTimeoutSeconds = coordinator.MaxTimeoutSeconds` (86400 s), directly sharing the constant from `coordinator`.
  - Defined `MaxExecutionTimeout = coordinator.MaxTimeout` (24 h) and `MinExecutionTimeout = 1 * time.Second`.
  - Defined internal conversion limits `maxDurationSeconds` and `minDurationSeconds`.
  - Implemented pure function `ClampExecutionTimeout(timeoutSeconds int) time.Duration`:
    - Clamps upper bound to `MaxExecutionTimeout` (86400 s).
    - Clamps lower bound to `MinExecutionTimeout` (1 s). Documented that non-positive timeouts violate the coordinator submission contract (SEC-014) and must not disable deadlines or trigger immediate context cancellation.
    - Guards against 64-bit integer multiplication overflow when converting to `time.Duration` nanoseconds.
    - Logs a structured warning (`slog.Warn`) per clamped assignment recording only numeric values (`original_timeout_seconds`, `clamped_timeout_seconds`).
  - Updated `ExecuteAndReport` to use `ClampExecutionTimeout`. Added optional `onContextDeadline` observer hook for non-sleeping test verification.
- `internal/worker/timeout_test.go`:
  - `TestClampExecutionTimeout`: table-driven unit test verifying clamping and overflow protection for 0, -1, 1, 86400, 86401, `math.MaxInt32`, `math.MaxInt64`, and multiplication overflow value `int(math.MaxInt64/1e9) + 1`.
  - `TestWorker_ExcessiveTimeoutClamped`: end-to-end worker test running against a fake coordinator returning a 10-year timeout (`10 * 365 * 86400` s) for a sleep task, asserting execution deadline is at most 86400 s.
