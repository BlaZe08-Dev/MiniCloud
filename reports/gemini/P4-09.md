# Slice P4-09 Final Report: SEC-012 Worker Execution Timeout Clamp (Docs Fix Round)

## 1. Problem & Architecture Review

Under finding **SEC-012**, the worker in `internal/worker/client.go` converted the assignment's `TimeoutSeconds` field directly to a `time.Duration` with no upper bound:
```go
execCtx, cancel := context.WithTimeout(ctx, time.Duration(assignment.TimeoutSeconds)*time.Second)
```
While the coordinator enforces a valid range of `[1, 86400]` seconds on job submission (SEC-014), in V1/V2 before mutual authentication and TLS are introduced (SEC-004), a network attacker or compromised coordinator could return an arbitrary multi-year timeout, holding worker execution slots indefinitely. Furthermore, on 64-bit systems, large values exceeding $9.22 \times 10^9$ seconds cause 64-bit integer multiplication overflow when converting to nanoseconds, producing negative durations.

Slice P4-09 resolves SEC-012 by:
1. Referencing the coordinator's existing maximum execution timeout bound (`coordinator.MaxTimeoutSeconds = 86400`) via a shared constant `MaxExecutionTimeoutSeconds` in `internal/worker/client.go` without duplicating literal values.
2. Implementing the pure function `ClampExecutionTimeout(timeoutSeconds int) time.Duration` that clamps upper values to 86400 s (24 h), clamps non-positive values up to 1 s, guards against 64-bit integer multiplication overflow, and logs a structured warning (`slog.Warn`) with numeric-only fields (`configured_seconds`, `effective_duration`).
3. Conducting an audit of all coordinator-supplied values used in the worker, fixing SEC-012, and registering three findings (**SEC-059**, **SEC-060**, and **SEC-061**) for coordinator boundary gaps.

## 3. Summary of Changes

### `internal/worker`
- `internal/worker/client.go`:
  - Defined `MaxExecutionTimeoutSeconds = coordinator.MaxTimeoutSeconds` (86400 s), directly sharing the constant from `coordinator`.
  - Defined `MaxExecutionTimeout = time.Duration(MaxExecutionTimeoutSeconds) * time.Second` (24 h) and `MinExecutionTimeout = time.Second` (1 s).
  - Defined internal conversion limits `maxDurationSeconds = int(math.MaxInt64 / int64(time.Second))` and `minDurationSeconds = int(math.MinInt64 / int64(time.Second))`.
  - Implemented pure function `ClampExecutionTimeout(timeoutSeconds int) time.Duration`:
    - Clamps upper bound to `MaxExecutionTimeout` (86400 s).
    - Clamps lower bound to `MinExecutionTimeout` (1 s). Documented that non-positive timeouts violate the coordinator submission contract (SEC-014) and must not disable deadlines or trigger immediate context cancellation.
    - Guards against 64-bit integer multiplication overflow when converting to `time.Duration` nanoseconds.
    - Logs a structured warning (`slog.Warn`) per clamped assignment recording only numeric values (`configured_seconds`, `effective_duration`).
  - Updated `ExecuteAndReport` to pass `timeout := ClampExecutionTimeout(assignment.TimeoutSeconds)` to `a.registry.Execute`.
- `internal/worker/timeout_test.go`:
  - `TestClampExecutionTimeout`: table-driven unit test verifying clamping and overflow protection for 8 cases: `zero_clamped_to_min` (0), `negative_clamped_to_min` (-1), `minimum_valid_unchanged` (1), `maximum_valid_unchanged` (86400), `above_maximum_clamped_to_max` (86401), `max_int32_clamped_to_max` (`math.MaxInt32`), `max_int64_clamped_to_max` (`math.MaxInt64`), and multiplication overflow case `multiplication_overflow_clamped_to_max` (`int(math.MaxInt64/int64(time.Second)) + 1`).
  - `TestWorker_ExcessiveTimeoutClamped`: end-to-end worker test running against a fake coordinator returning an assignment with a 10-year timeout (`const tenYearsSeconds = 10 * 365 * 86400` s) for a sleep task. Uses `deadlineObserverTask` wrapping `executor.SleepTask` registered into `executor.Registry` to observe `ctx.Deadline()` in `Execute` and verify the deadline does not exceed `start.Add(worker.MaxExecutionTimeout + 5*time.Second)`.
