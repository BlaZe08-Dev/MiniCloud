# MiniCloud State Machine & Lifecycle Specification

## 1. Overview
The job lifecycle in MiniCloud is governed by a formal finite state machine (FSM). All transitions are validated centrally by `internal/domain` rules. Any transition attempt outside the allowed transition matrix must be rejected with a typed error (`ErrInvalidStateTransition`).

---

## 2. Job States

| State | Classification | Meaning | Allowed Next States |
|---|---|---|---|
| `SUBMITTED` | Ephemeral / Initial | Job has passed schema validation and been recorded by the API. | `QUEUED`, `REJECTED` |
| `QUEUED` | Active / Pending | Job is waiting in the scheduling pool for an eligible worker. | `RUNNING`, `CANCELLED` |
| `RUNNING` | Active / In-Flight | An attempt has been dispatched and accepted by a worker under a lease. | `SUCCEEDED`, `RETRYING`, `FAILED`, `CANCEL_REQUESTED` |
| `CANCEL_REQUESTED` | Active / Draining | Cancellation was requested while an attempt was running; awaiting worker acknowledgement or termination. | `CANCELLED`, `SUCCEEDED`, `FAILED` |
| `RETRYING` | Active / Backoff | An attempt failed or timed out, and the job is eligible for another attempt within its retry policy. | `QUEUED`, `FAILED`, `CANCELLED` |
| `SUCCEEDED` | **Terminal** | A valid attempt result has been committed. | *None* |
| `FAILED` | **Terminal** | Execution failed permanently, or maximum attempt budget was exhausted. | *None* |
| `CANCELLED` | **Terminal** | Job was cancelled before execution started, or running attempt confirmed cooperative cancellation. | *None* |
| `REJECTED` | **Terminal** | Job submission was rejected before acceptance (e.g., unsupported task type, invalid payload bounds). | *None* |

## 3. Transition Matrix

The table below defines whether a transition from `Current State` (rows) to `Target State` (columns) is permitted:

| From \ To | `SUB` | `QUE` | `RUN` | `CAN_REQ` | `RET` | `SUC` | `FAI` | `CAN` | `REJ` |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| **`SUBMITTED`** | — | **YES** | NO | NO | NO | NO | NO | NO | **YES** |
| **`QUEUED`** | NO | — | **YES** | NO | NO | NO | NO | **YES** | NO |
| **`RUNNING`** | NO | NO | — | **YES** | **YES** | **YES** | **YES** | NO | NO |
| **`CANCEL_REQUESTED`** | NO | NO | NO | — | NO | **YES** | **YES** | **YES** | NO |
| **`RETRYING`** | NO | **YES** | NO | NO | — | NO | **YES** | **YES** | NO |
| **`SUCCEEDED`** | NO | NO | NO | NO | NO | — | NO | NO | NO |
| **`FAILED`** | NO | NO | NO | NO | NO | NO | — | NO | NO |
| **`CANCELLED`** | NO | NO | NO | NO | NO | NO | NO | — | NO |
| **`REJECTED`** | NO | NO | NO | NO | NO | NO | NO | NO | — |

*Note: Terminal states (`SUCCEEDED`, `FAILED`, `CANCELLED`, `REJECTED`) are strictly immutable. No transition away from a terminal state is permitted under any circumstances.*

## 4. Attempt Lifecycle

Each job execution generates a separate, explicitly tracked `Attempt`:
- `attempt_no`: Monotonically increasing 1-based integer (`1, 2, 3...`).
- `attempt_id`: Unique identifier (UUID/timestamp-based).
- `lease_token`: Opaque string generated by the coordinator upon dispatch.
- `state`: Attempt state (`PENDING`, `RUNNING`, `COMPLETED`, `FAILED`, `EXPIRED`, `CANCELED`).

```text
       [Dispatch Job]
             │
             ▼
        (PENDING)
             │
             │ Worker claims / starts
             ▼
        (RUNNING)
        /    │    \
       /     │     \
[Success] [Failure] [Lease Expired / Worker Lost]
     │       │       │
     ▼       ▼       ▼
(COMPLETED)(FAILED)(EXPIRED)
```

## 5. Critical Invariants

1. **Unique Identity:** A job has a stable immutable ID across all retries. Each execution has a distinct `attempt_id` and monotonic `attempt_no`.
2. **Commit Authority:** Only the attempt matching the job's current `attempt_id` and holding a valid `lease_token` can transition the job to `SUCCEEDED` or `FAILED`.
3. **Stale Result Rejection:** If an old worker returns a result after its lease expired or after a newer attempt has started, the coordinator rejects the commit with `ErrStaleAttempt` (HTTP 409 Conflict).
4. **Single Terminal Commit:** Exactly one terminal outcome is recorded per job. Once a job reaches `SUCCEEDED`, `FAILED`, `CANCELLED`, or `REJECTED`, all subsequent outcome reports are ignored or logged as diagnostics.
5. **Bounded Execution:** Maximum attempts are bounded by `max_attempts` (default 3). Exceeding `max_attempts` transitions the job to `FAILED`.
6. **Lease Expiry Semantics:** A lease expiration proves that the coordinator stopped trusting the worker; it does not prove the worker process halted. Hence, subsequent result reporting by that worker is safely blocked by lease token mismatch.
