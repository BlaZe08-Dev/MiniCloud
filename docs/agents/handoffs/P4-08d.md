## Security review
Assumptions challenged:
- A pass during grace cannot push a worker toward fallback (`TestConformance_AssignPass_GraceRevokesWithoutCounting`, both backends; the loop tests).
- A failing loop pass cannot open the age arm for polls (`TestCoordinator_AssignmentLoop_RateLimitedPoll_NoAgeClaim`).
- 100 workers polling 1,000 times cannot start more than one refresh per interval (`TestPoll_RefreshAttempts_AtMostOnePerInterval`).
- A deep backlog cannot hold `s.mu` across repeats (`TestCoordinator_AssignmentRepeat_YieldsToPolls`).
- A bad setting or policy cannot start the binary (`TestMain_ConfigureService_FailsOnInvalidAssignmentSettings`, `TestMain_ConfigureService_FailsOnRejectedPolicy`). Config and service cannot drift apart silently (`TestMain_AssignmentSettings_ConfigAndServiceAgree`).
- The log line holds the policy and durations only; no URL or secret (`TestMain_ConfigureService_AppliesDispatchPolicyAndSettings` checks the exact attribute set).

Findings:
- **F-5c-1, minor, inferred (not tested, not measured).** Each submit adds at most one pass (the trigger buffer is one), but rounds triggered back to back have no yield between them; the yield applies only to repeats inside a round. The submit endpoint is unauthenticated (SEC-004, accepted), so a submit flood can run passes continuously. A waiting poll still competes for `s.mu` between rounds. Go's mutex hands a lock to a waiter that has waited over 1 ms (from the `sync` package documentation, not measured here). Part 2's abuse suite (FS-24) is the place to measure it.
- No other finding.

Not tested: several coordinators; a real database outage during the loop (part 2, FS-20); the binary started as a process (the wiring is tested through `configureService` and `startBackground`).
