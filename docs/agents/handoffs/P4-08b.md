## Questions for the orchestrator

These are places where the ADR is silent or internally inconsistent. I made the reading noted and did not change the ADR.

1. Lapse cap and the pass (D9 vs Section 2.1). D9 says a job whose lapses reach `MAX_LAPSES` "leaves round-robin". Section 2.1's candidate read does not exclude such jobs. I implemented D9: the pass does not reserve a job at the lapse limit, so it becomes claimable by the lapse arm. Confirm.
2. Refresh location (Section 7). Section 7's 5a scope does not list the poll-time refresh, but 5a's tests INV-19, INV-23 and INV-24 (memory variants) need it, and FS-23 says "slice 5a (memory)". Section 7's 5c scope lists "the poll-time refresh". I implemented the memory refresh in 5a. Confirm.
3. Freshness write before refresh (Section 2.2). The ADR says `last_poll_at` is set on claim and on 204, and does not say whether the write precedes the refresh. Without a write before the refresh, a poller's own refresh cannot reserve to it (INV-19 requires it to). I write freshness first. Confirm.
4. Effective-slot constant location (Section 2.4). The ADR places `effectiveWorkerSlots` in the coordinator, but the pass lives in the storage package. I put `domain.EffectiveWorkerSlots` in domain. Confirm.
5. Memory test name for INV-1 (Section 6.3). The ADR names only the Postgres test. I used `TestConformance_ClaimAssigned_ConcurrentPollsOneWinner` for the memory variant. Confirm the name.
6. Shared conformance runner. `AssignmentRepository` is not in `Repository`, so the shared `storagetest` runner cannot cover the assignment cases yet. The cases live in `storage_test`, with Postgres skips in the `postgres` package. Confirm this is acceptable until 5b.
