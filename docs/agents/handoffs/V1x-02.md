## Design decisions and deviations
- The header is set only in `writeJSON` (no middleware sets it; confirmed by grep). The 204 poll response (`w.WriteHeader(http.StatusNoContent)`, no body) does not go through `writeJSON` and has no header; no body, so nothing to sniff.
- Deviation from the task text, found by running it: `encoding/json` escapes U+2028 and U+2029 in plain string values even with `SetEscapeHTML(false)`. Poll payloads are `json.RawMessage`, which is copied without that escaping, so the bug path is fixed (T1 passes for U+2028/U+2029). Plain string fields (for example error messages) keep ` `. No path carries a payload in a plain string. T5 therefore asserts `< > &` raw and does not assert U+2028 raw. Evidence label: executed (see report).

## Security review
- Assumption challenged: that `SetEscapeHTML(false)` unescapes U+2028/U+2029 everywhere. Tried it (executed): false for plain strings, true for `json.RawMessage`.
- Attack: raw `<` and `>` in JSON bodies (sniffing). Guard: `nosniff` plus `application/json`, tested by `TestAPI_NosniffHeaderOnEveryWriteJSONResponse`. Browser behaviour itself was not tested (designed, not executed).
- Not tested: responses written by the standard library (ServeMux 404/405 text/plain, MaxBytesReader errors); they carry no user JSON.
- Findings: none new.
