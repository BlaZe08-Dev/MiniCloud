## What changed (by package)

- `internal/domain/failure.go` (new): `IsFailedOutcome`, `NormalizeWorkerErrorClass` (PERMANENT/TRANSIENT/UNKNOWN only, omitted on failure means UNKNOWN, LEASE_EXPIRED and anything else rejected with `ErrInvalidRequest`, a class on a success rejected, the rejected value never echoed), `ResolveFailure` (the single decision: cancel wins, PERMANENT fails, retry while `attempt_no < max_attempts`, otherwise FAILED/exhausted).
- `internal/storage`: `Repository.CommitAttempt` gained a trailing `backoff domain.BackoffFunc` (same shape the sweeper already takes). Both `InMemoryRepository.CommitAttempt` and `postgres.Repository.CommitAttempt` call `domain.ResolveFailure` under the job lock: retry sets `RETRYING`, `not_before = now + backoff(attempt_no)` (repository clock / `clock_timestamp()`), no results row, `JOB_RETRYING` event; PERMANENT or exhausted sets `FAILED` with results row and `JOB_FAILED` (details `error_class`, `attempt_no`, and `error: "max attempts exhausted"` when the budget ran out); a failure on `CANCEL_REQUESTED` sets attempt `FAILED` (class stored) and job `CANCELLED`, results row stored, `JOB_CANCELLED`. A retryable failure with a nil backoff is rejected before any write. In-memory `ListAttemptsByJob` now sorts by `attempt_no` (it returned map order; found by `-count=20`).
- `internal/coordinator`: `CommitResult` takes the worker's `errorClass`, validates it up front, passes `retryBackoffLocked()` (`domain.ComputeBackoff` over the existing random source, shared with the sweeper; no second implementation). `SetDefaultMaxAttempts` / `DefaultMaxAttempts`.
- `internal/api`: `ReportResultRequest.ErrorClassification` (`error_classification`, protocol 4.4/6.2); submit without `max_attempts` uses the coordinator default.
- `internal/config`: `MINICLOUD_DEFAULT_MAX_ATTEMPTS` validated in 1..20. `cmd/coordinator`: `configureService` now returns an error and applies the default.
- `internal/executor/classify.go` (new): `Classify` (validation, unknown task, oversized payload: PERMANENT; deadline: TRANSIENT; else including cancellation: UNKNOWN).
- `internal/worker`: `ReportResult` sends `error_classification` for failures; `ExecuteAndReport` classifies via `executor.Classify`.
- `cmd/mc`: `mc get` prints a Failure section (outcome, attempts used of max, last class and error, next retry time) from the job and its attempts; `mc attempts` shows a CLASS column.

## Design decisions and deviations (with reasons)

1. **No new protocol field.** Failure presentation uses fields the API already serves: job `state`/`max_attempts`/`not_before`/`result`, attempt `state`/`error_class`/`error` (emitted since 4b). `mc get` makes a second call to the attempts endpoint. See open question 1.
2. **`CommitAttempt` signature change.** Added `backoff` as a parameter (like `SweepParams.Backoff`) instead of hidden randomness or a repository option; about 40 call sites updated mechanically (own commit, behaviour unchanged).
3. **Results row on cancel-wins failure.** The worker's outcome is stored in `results` and shown as `result` on the CANCELLED job. Docs do not say either way (open question 2). A RETRYING job has no results row (the table is one row per job).
4. **Class on a success is rejected (400).** Protocol says the field is omitted on success; I chose strict rejection over silent ignore so a COMPLETED attempt can never carry a class.
5. **Deadline is TRANSIENT.** ADR-0015 lists "context deadline" among abnormal terminations without a class (open question 3). Retries stay bounded by `max_attempts`.
6. **Validation order.** The class check happens before state checks, so a stale worker sending LEASE_EXPIRED gets 400 rather than 409 (protocol 6.3 has no 400 row).
7. **`mc submit --max-attempts` default 0 = omit.** It used to always send 3, which made `MINICLOUD_DEFAULT_MAX_ATTEMPTS` unreachable from the CLI. This is slightly outside "failure presentation only"; needed for the setting to be wired end to end. Authorisation: the task text ("wire DEFAULT_MAX_ATTEMPTS"), not an owner decision.
8. Model conformance test (`RunStateMachineModelConformance`) updated: failure commits now follow the new outcomes (an hour of backoff keeps RETRYING jobs out of the model's FIFO poll; cancel of RETRYING added). Not a weakened assertion: it models the new design.
9. Not touched: SEC-012 timeout logic, round-robin, fault injection, authentication.

## Open questions for the orchestrator

1. Protocol 3.3 lists neither `error_class` nor the other additive attempt fields the code already serves; `mc` now relies on `error_class`/`error`. Docs pass should list them. If a dedicated job-level failure field is wanted instead, that needs an owner decision.
2. Should a cancel-wins failure store a `results` row (current) or leave the CANCELLED job without a result?
3. Is a task deadline TRANSIENT (current) or should it be PERMANENT/UNKNOWN? ADR-0015 is silent.
4. Protocol 4.4 says the class is "omitted on success"; I reject a class on a success with 400. Confirm.
5. `mc submit --max-attempts` default changed to "use the coordinator default" (deviation 7).

## Security review

Assumptions challenged: the worker's class is untrusted (a worker could pick PERMANENT to end a job early or TRANSIENT to burn its attempts: bounded by `max_attempts`, accepted under SEC-004, no authentication in V1); LEASE_EXPIRED is the sweeper's alone; cancel must beat any retry; the retry delay must come from the one backoff function; unbounded input in the class field must not be echoed or stored.

Attacks tried (executed): LEASE_EXPIRED, unknown, lowercase and a 70,000-byte class value against the service, API and both repositories (`TestCoordinator_CommitResult_FailureClassification`, `TestAPI_ReportResult_ErrorClassification`, `TestConformance_CommitAttempt_FailureRetryOrFail`): all rejected with 400/`ErrInvalidRequest`, nothing written, attempt still committable. A class on a success rejected. Failure racing cancel for every class and on the last attempt (`TestConformance_CommitAttempt_FailureOnCancelRequestedYieldsCancelledJob`, `TestAPI_CancelJob_RunningRaces`): always CANCELLED, never RETRYING, never re-dispatched after an hour. Replayed failure commit on the CANCELLED job and a second cancel: 409. Nil backoff: rejected before any write. Model-based random sequences with the new outcomes against both repositories (`TestProperty_StateMachine_ModelConformance`).

Not tested: authentication (SEC-004), multi-worker contention on a retried job under concurrent commit and sweep at scale (slice 4e stress), oversize `error` text through the new retry path, hostile `error` content in `mc` output (printed as is).

Findings:
- Note on provisional label: The label "SEC-029" used here provisionally was retired (that in-memory ordering bug was a fixed correctness bug, not a security finding; the canonical SEC-029 in findings.md is the Makefile destructive targets finding). In-memory `ListAttemptsByJob` returned attempts in map order while Postgres orders by `attempt_no`; with retries the attempt history (and `mc attempts`) could appear in any order. Evidence: `-count=20` failure of `TestAPI_ReportResult_ErrorClassification`; conformance assertion red 3 of 40 then green.
- No other new finding. `error_class` from workers is limited to bounded constants and never echoed.
