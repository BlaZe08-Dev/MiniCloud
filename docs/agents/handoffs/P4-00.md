## Security review
- **Assumptions challenged**:
  - *Assumption*: Duplicate `CancelJob` calls on a `CANCEL_REQUESTED` job were harmless idempotent operations.
    - *Result*: Proven false by audit probe `TestReviewP400_SEC022_DoubleCancelLeaksWorkerSlot` (planned test). The storage layer transitioned the job immediately to `CANCELLED`, causing the worker's subsequent cooperative commit to be rejected with 409 `JOB_ALREADY_TERMINAL`, leaving the attempt `RUNNING` in the database and permanently leaking worker slot capacity (SEC-022). Resolved by making duplicate cancel an idempotent repository no-op returning HTTP 200 with state `CANCEL_REQUESTED`.
  - *Assumption*: Leases expired automatically on the database clock and should immediately block renewal or commit requests.
    - *Result*: Proven flawed. Requiring unexpired leases on renewal or commit caused cascading aborts during coordinator restarts or transient network delays. Resolved by the symmetric accept-until-swept rule: exclusive rights persist until the background sweeper reaps the attempt to `LOST`.
  - *Assumption*: Coordinator sweeper could use wall-clock timestamps or `/readyz` connectivity to detect database outages.
    - *Result*: Proven ungrounded. `/readyz` only measures coordinator-to-DB ping reachability, not background sweeper tick health. Wall-clock gaps drift under NTP or VM pause. Resolved by using database-clock timestamps (`clock_timestamp()`) and measuring tick execution gaps (> 3x sweep interval) with autonomous 30s grace windows and 30s cooldown.
  - *Assumption*: PostgreSQL sweeper could combine `SKIP LOCKED` and `NOWAIT`.
    - *Result*: Proven invalid SQL syntax in PostgreSQL. Replaced with canonical locking: `SELECT jobs ... FOR UPDATE SKIP LOCKED`, followed by plain `FOR UPDATE` on workers and attempts under `lock_timeout`.
