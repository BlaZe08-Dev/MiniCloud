## Design decisions and deviations from the design doc (with reasons)

- **D1 (scope not built; owner decision 2 recorded).** The plan's Slice 4a Scope also lists in-memory `RenewLease`, `SweepExpiredLeases` and the two grace timers, with gating test `TestInMemoryRepository_LeaseRenewalAndExpiry` (planned test). Not built here, by owner decision: `RenewLease` moves to slice 4b (lands with migration 000004 and the PostgreSQL implementation); `SweepExpiredLeases`, the grace timers and `TestInMemoryRepository_LeaseRenewalAndExpiry` (planned test) move to slice 4c. Reasons they could not be built in 4a: they need `storage.Repository` interface additions that the PostgreSQL repository must implement, its `lease_expires_at` column does not exist until migration 000004, and the sweeper needs 4d's backoff. Domain fields (`Attempt.LeaseExpiresAt`, `Job.NotBefore`, `Job.CancelRequestedAt`) and `not_before` evaluation in memory dispatch are done. The exact plan text for the move is in the next section.
- **D2 (allowlist).** The plan says the path entry and "the two real test names" go stale. The checker reported exactly two stale entries (the path, and `TestReviewP400_SEC022_DoubleCancelLeaksWorkerSlot`); I removed those two. `TestReviewP400_SEC022` stays (plan). `TestReviewP400_OldCoordinator_RenewRouteResponse` stays because that test was deliberately not brought over and the checker did not flag it.
- **D3 (`NewServiceWithQueue`, fix pass: retired).** Plan sentence (phase4-plan.md, Slice 4a item 4): "`NewServiceWithQueue` ... and its queue parameter (still passed in `tests/integration/multi_worker_batch_test.go:39-40`) are candidates for owner approval (propose deprecation/retirement or compatibility wrapper)." That leaves the choice open, so per the fix-pass rule I retired it: the function is deleted, the only in-repo caller (`tests/integration/multi_worker_batch_test.go`) already uses `NewService`, and no test references it. (The first pass had kept a deprecated wrapper with an ignored `any` parameter; removed because an ignored parameter is a trap.) Historical documents (ADR-0008, CHANGELOG) still mention the constructor; they describe past state and are not edited here.
- **D4 (findings.md).** The task said "only the SEC-022 status line". SEC-022 has two status places (the table row cell and the `**Status**` line of the detailed entry). I changed both to "Fixed in slice 4a (executed)"; in the fix pass the table row's evidence column was also set to `TestReviewP400_SEC022_DoubleCancelLeaksWorkerSlot` (regression test, executed in slice 4a). Nothing else in that file was touched.
- **D5 (diagnostic event).** Written for any attempt that exists and belongs to the rejected job, once per attempt (memory: scan under the mutex; PostgreSQL: `NOT EXISTS` under the job row lock). Attempt IDs that do not exist or belong to another job record nothing, so unauthenticated junk IDs cannot grow `job_events` (SEC-004 bound). Details are `{attempt_id, reporting_worker, rejected:true}`. Slice 4b's partial unique index will arbitrate the same rule in SQL.
- **D6 (closing rule).** The attempt is closed only if it is `RUNNING` and equals the job's `current_attempt_id` (ADR-0014 evaluation order item 1), exactly as the ADR words it. An attempt of the same job that is not current and RUNNING is not touched; I could not construct that state through the public API, so this branch is untested.
- **D7 (parity gaps until 4b).** `CancelRequestedAt` is stamped in memory only (PostgreSQL has no column yet). In-memory `ListQueuedJobs` lists due RETRYING jobs; PostgreSQL still lists only QUEUED. PostgreSQL `DispatchNextJob` does not dispatch RETRYING jobs yet. Conformance tests therefore assert none of these on PostgreSQL; `RunCancelRetryingImmediatelyCancelledConformance` forces RETRYING with SQL and passes on both because PostgreSQL's cancel already fell through to `CANCELLED`.
- **D8 (probe semantics).** After the fix the SEC-022 probe passes if either the duplicate-cancel fix or the terminal-commit cleanup is present (mutation m1e shows PostgreSQL duplicate-cancel removal alone does not fail it; m1f shows it fails when both are removed). The conformance tests pin each fix separately.
- **D9 (plan statements checked).** The plan says no existing test asserts a second cancel on `CANCEL_REQUESTED`; I found none either. Plan item 1(d) (Invariant 4 in `TestPostgresRepository_Concurrency_MixedOperationsStress`) is done.

- **Q-4c-1 (for the 4c spec): does the sweeper's retry-or-fail decision need slice 4d's classification?** The plan's sweeper rules (Slice 4b, R-02) decide by attempt count only: the attempt becomes `LOST` with `error_class = LEASE_EXPIRED`, then the job goes to RETRYING with backoff if `attempt_no < max_attempts`, else FAILED. A lease expiry is by definition `ClassLeaseExpired`, so the sweeper does not need the worker-reported classification (PERMANENT, TRANSIENT, UNKNOWN) that 4d adds for `CommitAttempt`. What it does need from 4d is the backoff function (`not_before = now + jittered exponential`, base 1s, cap 30s). Proposed ordering: in 4c the sweeper takes the backoff through a small injectable dependency (a `Backoff(attemptNo) time.Duration` function) with a fixed deterministic implementation (for example the unjittered exponential), so 4c is testable without 4d; 4d then swaps in the full-jitter policy and adds classification of reported failures, with no change to the sweeper's decision code. Building 4d's policy first would make 4c wait on 4d. ADR-0015's rule that `LOST` attempts consume `max_attempts` stays the only decision input.

## Security review

**Assumptions challenged**
- S1. **Terminal-job close: what the caller must present, check order, effect of a wrong value (owner decision 3: confirmed intended, Informational, inside SEC-004; code unchanged).** From the code (in-memory `CommitAttempt` and `rejectTerminalCommitLocked`; PostgreSQL `CommitAttempt` and `rejectTerminalCommit`):
  - **Presented:** only the job ID (to find the job) and the attempt ID (to name the attempt). The lease token and worker ID are parameters of the function but are not examined on the terminal path; the worker ID is only copied into the diagnostic event's `reporting_worker`. No token comparison and no worker comparison happens before or during the close.
  - **Order, in-memory (single mutex):** job exists (`ErrJobNotFound`) -> job terminal? If yes, `rejectTerminalCommitLocked` runs and the call returns `ErrJobAlreadyTerminal`. Only for a non-terminal job do the later checks run: attempt equals the job's current attempt (`ErrStaleAttempt`), attempt exists (`ErrAttemptNotFound`), attempt RUNNING (`ErrStaleAttempt`), constant-time token hash comparison (`ErrStaleAttempt`), worker match (`WorkerMismatchError`).
  - **Order, PostgreSQL (one transaction):** `SELECT ... FROM jobs ... FOR UPDATE` (`ErrJobNotFound` if absent) -> job terminal? If yes: `rejectTerminalCommit` (`SELECT job_id, state FROM attempts WHERE id = $1 FOR UPDATE`, the conditional close, then the `INSERT ... WHERE NOT EXISTS` diagnostic), `tx.Commit`, then `ErrJobAlreadyTerminal`. Only for a non-terminal job does the existing sequence run: current-attempt match, attempt row lock, attempt RUNNING, constant-time token comparison, worker match.
  - **Effect per input on a terminal job:** (1) the job's current attempt ID, attempt still RUNNING: attempt becomes CANCELLED (job CANCELLED) or LOST (job SUCCEEDED or FAILED), slot freed, one diagnostic event; any token or worker value works. (2) Same attempt ID with a wrong or missing token: identical to (1), because the token is not examined (the confirmed-intended behavior; untested with a wrong token). (3) An attempt ID that does not exist: nothing closed, no event (test `unknown_attempt_records_nothing`). (4) An attempt ID that exists but belongs to another job: nothing closed, no event (test `foreign_attempt_is_not_closed`). (5) The attempt ID of an attempt already COMPLETED, FAILED, CANCELLED or LOST: attempt not modified, the diagnostic event is still written once (test `completed_attempt_never_overwritten` covers the not-overwritten part). In every case the job and the stored result are unchanged and the HTTP result is 409 `JOB_ALREADY_TERMINAL`.
  - **Impact:** it can only move a RUNNING attempt of an already-terminal job to CANCELLED or LOST, the state the invariant demands anyway, and write at most one diagnostic event per attempt. Informational. Evidence: confirmed by code reading; executed for cases (3), (4) and the valid-token variants of (1) and (5); the wrong-token variant of (1)/(2) is **not** tested.
- S2. "Rejected commit rolls back" was the old behavior; the cleanup must survive the rejection. PostgreSQL now commits the cleanup transaction before returning the error. If that commit or a cleanup statement fails, the caller gets a database error (HTTP 500 path) instead of 409; the job is never mutated. Evidence: confirmed by code reading; not fault-injected.
- S3. Unbounded diagnostic growth under unauthenticated calls (SEC-004): bounded by one event per (job, attempt); attempt IDs that do not exist or belong to another job record nothing. Evidence: executed (`foreign_attempt_is_not_closed`, `unknown_attempt_records_nothing`, mutations m2e-m2g).
- S4. Attacker-controlled `reporting_worker` stored in event details: length and charset bounded by the API's `isValidIdentifier`; the repository trusts that; not re-validated in the repository. Evidence: confirmed by code reading.
- S5. Closing an attempt of another job by naming it on a terminal job's commit: prevented by the job-ownership check. Evidence: executed (`foreign_attempt_is_not_closed`, mutations m2c/m2d).
- S6. Overwriting a COMPLETED/FAILED attempt or the stored result by replaying a commit: prevented. Evidence: executed (`completed_attempt_never_overwritten`, mutations m2a/m2b; the model test replays commits on terminal jobs).
- S7. Duplicate cancel could still finalise a job through another path: model test (cancel after cancel, commit after cancel) shows no divergence over 8 + 3 seeds. Evidence: executed.

**Attacks tried (real tests)**: double cancel then late commit then poll (`TestReviewP400_SEC022_DoubleCancelLeaksWorkerSlot`); triple cancel (`TestConformance_CancelJob_IdempotentCancelRequested`); commit replay on terminal job, with the original and different payloads (`completed_attempt_never_overwritten`); commit naming another job's attempt (`foreign_attempt_is_not_closed`); commit naming nonexistent attempts, three times (`unknown_attempt_records_nothing`); 60-goroutine mixed operations with an Invariant 4 query (`TestPostgresRepository_Concurrency_MixedOperationsStress`).
