# Handoff P4-09 — SEC-012 worker execution timeout clamp

Branch: `agent/gemini/P4-09`

## What changed (by package)

### `internal/worker`
- `internal/worker/client.go`:
  - Added named constant `MaxExecutionTimeoutSeconds = coordinator.MaxTimeoutSeconds` (86400 s) in `internal/worker/client.go` referencing the coordinator's existing upper bound rather than duplicating its value.
  - Defined `MaxExecutionTimeout = time.Duration(MaxExecutionTimeoutSeconds) * time.Second` (24 h) and `MinExecutionTimeout = time.Second` (1 s).
  - Defined internal conversion limits `maxDurationSeconds = int(math.MaxInt64 / int64(time.Second))` and `minDurationSeconds = int(math.MinInt64 / int64(time.Second))` for safe `time.Duration` conversion on 64-bit platforms.
  - Implemented pure function `ClampExecutionTimeout(timeoutSeconds int) time.Duration`:
    - Clamps values above `MaxExecutionTimeoutSeconds` (86400 s) down to `MaxExecutionTimeout` (86400 s).
    - Clamps values below `1` s up to `MinExecutionTimeout` (1 s). Documented that tasks require a positive execution deadline; non-positive timeouts violate the coordinator's submission contract (SEC-014) and must not disable deadlines or trigger immediate context cancellation.
    - Guards against 64-bit integer multiplication overflow when converting `timeoutSeconds` to `time.Duration` nanoseconds: values exceeding `maxDurationSeconds` return `MaxExecutionTimeout`, and values below `minDurationSeconds` return `MinExecutionTimeout`.
    - Logs a structured warning (`slog.Warn`) per clamped assignment recording only numeric values (`configured_seconds`, `effective_duration`), preventing attacker-sized strings in logs.
  - In `ExecuteAndReport`, replaced direct unbounded duration calculation `time.Duration(assignment.TimeoutSeconds) * time.Second` with `timeout := ClampExecutionTimeout(assignment.TimeoutSeconds)` passed into `a.registry.Execute`.
- `internal/worker/timeout_test.go`:
  - Implemented table-driven unit test `TestClampExecutionTimeout` exercising 8 test cases: `zero_clamped_to_min` (0), `negative_clamped_to_min` (-1), `minimum_valid_unchanged` (1), `maximum_valid_unchanged` (86400), `above_maximum_clamped_to_max` (86401), `max_int32_clamped_to_max` (`math.MaxInt32`), `max_int64_clamped_to_max` (`math.MaxInt64`), and multiplication overflow case `multiplication_overflow_clamped_to_max` (`int(math.MaxInt64/int64(time.Second)) + 1`).
  - Implemented end-to-end worker test `TestWorker_ExcessiveTimeoutClamped` using a fake coordinator HTTP server that returns an assignment with a 10-year timeout (`const tenYearsSeconds = 10 * 365 * 86400` s) for a sleep task. Uses `deadlineObserverTask` wrapping `executor.SleepTask` registered in `executor.Registry` to observe `ctx.Deadline()` in `Execute` and verify the deadline does not exceed `start.Add(worker.MaxExecutionTimeout + 5*time.Second)`.

## Security review
- **Assumptions challenged**:
  - Assumed coordinators are always trusted and will never send malicious timeout values: refuted by SEC-012. In V1/V2 before mutual authentication and TLS are introduced (SEC-004), an attacker on the loopback or network could forge coordinator responses with multi-year timeouts, pinning worker concurrency slots indefinitely.
  - Assumed converting `int` seconds to `time.Duration` nanoseconds is safe from overflow: refuted. In Go on 64-bit architectures, `time.Duration` is an `int64` of nanoseconds. An integer timeout greater than $9,223,372,036$ seconds overflows 63-bit signed integer limits during multiplication by $10^9$, wrapping to negative values. Without explicit overflow guarding, negative durations bypass upper bound checks and get clamped to the lower bound (1 s).
  - Assumed non-positive timeouts could disable deadlines: refuted. The coordinator rejects non-positive timeouts at the API boundary (SEC-014); the worker must never allow zero or negative durations to cancel execution immediately or disable timeouts.
- **Attacks tried**:
  - 10-year excessive timeout attack (`10 * 365 * 86400` s): clamped to 86400 s (`MaxExecutionTimeout`) in end-to-end worker execution [executed].
  - 64-bit integer overflow attack (`math.MaxInt64` and `9223372037` s): clamped safely to 86400 s without integer wrap-around [executed].
  - Non-positive timeout injection (`0` and `-1` s): clamped safely to 1 s (`MinExecutionTimeout`) [executed].
- **Not tested**:
  - Worker behavior under system clock jumps during task execution (mitigated by Go runtime's monotonic timer backing `time.Now()` and context deadlines).
- **Findings with evidence labels**:
  - **SEC-012** (Informational, Worker / Network Boundary): Worker execution timeout unbounded on assignment receipt. Status: **Confirmed, Fixed (Slice P4-09)** [executed]. Verified via `TestClampExecutionTimeout` and `TestWorker_ExcessiveTimeoutClamped`.
  - **SEC-059** (Informational, Worker / Network Boundary): `renewalInterval` lacks explicit multiplication overflow guard on `LeaseDurationSeconds` before duration clamping. Status: **Open** [confirmed by code reading].
  - **SEC-060** (Low, Worker / Network Boundary): In `internal/worker/client.go` func `pollWork`, HTTP response body decodes (lines 298, 318) are unbounded without `io.LimitReader`. Status: **Open** [confirmed by code reading].
  - **SEC-061** (Informational, Worker / Network Boundary): Worker request URLs in `renewOnce` (line 410) and `reportResult` (line 355) interpolate unescaped `JobID` and `AttemptID` identifiers. Status: **Open** [confirmed by code reading].
