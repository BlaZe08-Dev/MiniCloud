## Design decisions and deviations from the design doc (with reasons)

1. **Staleness on the repository clock through a new interface.** Note 8 requires that the Service never compare its own clock with a repository time; the task also says to keep the interface in `internal/storage/assignment.go` as it is. I added `storage.AssignmentPassStaleness` in a separate file. Open question 1.
2. **Pass heartbeat time.** Superseded by fix round 1: the heartbeat is written with `clock_timestamp()` in the last statement (ADR-0017 implementation note 12). The first round wrote `now()` (transaction start), as note 8 says literally, and raised open question 2.
3. **Advisory key** `AssignmentPassLockID = 0x4d43417373676e` ("MCAssgn"). The ADR fixes no value; it differs from the migrator's `DefaultAdvisoryLockID`.
4. **Lock timeout of the pass** reuses the sweep lock timeout (`WithSweepLockTimeout`, default 5 s), as Section 2.4 says ("the bounded `lock_timeout` already used by the sweeper").
5. **After a worker lock timeout, the decision continues** with the next successor (Section 2.4 says the worker is skipped for the rest of the pass, and is silent about the decision). `TestPostgresRepository_Assign_SkipsWorkerLockedByClaim` pins this: the job goes to `w_2`.
6. **Commit and sweep are not changed.** They start from RUNNING, where the shape CHECK already forbids a reservation, so there is nothing to clear; the INV-2b test asserts that the columns stay NULL through both.
7. **SQL is written as complete literals.** My first version built the queries by concatenating constant fragments. `TestPostgresRepository_Security_ASTCheck_NoDynamicSQLConcatenation` failed on six call sites (logged in the scratchpad run, not in the evidence directory); I rewrote the queries as literals and did not change the security test.
8. **In-memory `DispatchJob` parity.** PostgreSQL must clear the reservation (the CHECK), so memory now does too.
9. **Migration test reshaped.** `TestMigrator_Migration000004_FreshSchema` required exactly four migrations; it now requires at least four with 000004 fourth, and `TestMigrator_Migration000005_FreshSchema` pins five. The two 000004 upgrade tests now apply exactly up to 000004 (with `postgres.NewMigrator()` they would also apply 000005).

## Security review

Assumptions challenged:
- Two polls cannot both claim one job (`TestPostgresRepository_ClaimAssigned_ConcurrentPollsOneWinner`, 16 concurrent polls with the age arm open for all).
- A connection that holds a worker row cannot stall the pass past `lock_timeout` or make it reserve that worker (`TestPostgresRepository_Assign_SkipsWorkerLockedByClaim`).
- A connection that holds a job and then asks for a worker cannot deadlock the pass (`TestPostgresRepository_AssignmentPass_NoDeadlockWithClaim`, and the mixed concurrent test).
- A held advisory key cannot block a pass or make it write (`TestPostgresRepository_AssignmentPass_SecondPassSkips`).
- No path can leave a reservation on a RUNNING or terminal job (`TestPostgresRepository_CancelAssigned_ClearsAssignment`, `TestMigrator_Migration000005_FreshSchema`).
- SQL is never built by concatenation (the existing AST check passes).

Not tested: worker deletion with a reservation (question 5), several coordinators, the poll-write throttle under a flood (5c), sybil workers (SEC-004, accepted gap, unchanged).

Findings:
- **F-5b-1, minor, executed.** `Service.SubmitJob` in `internal/coordinator/service.go` stamps `created_at` with the coordinator's process clock, and the PostgreSQL `SubmitJob` stores that value. The age arm compares `GREATEST(created_at, not_before)` with `clock_timestamp()`. A process clock ahead of the database clock makes jobs look younger (late age claims); a clock behind makes them look older (early age claims). Evidence: with the test's process clock at 2026-10-31 12:00 UTC (minutes ahead of the database clock), `TestPoll_RateLimitedPoll_NoAgeClaim` and `TestFault_AssignmentPassStalled_JobRunsWithinBound` failed: no age claim was possible (`P4-08c-evidence/finding-created-at-process-clock.log`). The tests now start the process clock at database time; the code is not changed. The same value orders FIFO dispatch (`ORDER BY created_at`), which is pre-existing behaviour. Suggested fix, for the orchestrator to decide: let PostgreSQL stamp `created_at` with the database clock. Not entered in `docs/security/findings.md`, which this task does not own.
- No other finding.

Evidence labels: the gate counts and mutation results are executed; the EXPLAIN plans are executed (2,000 rows, one run); question 5 is inferred; the ADR statements are confirmed by code reading.
