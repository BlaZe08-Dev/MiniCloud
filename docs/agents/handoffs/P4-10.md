## Design decisions and deviations from the design doc (with reasons)
- `MaxPollResponseBytes` value: Set to `6*executor.MaxPayloadSizeBytes + 64*1024` (448 KiB / 458,752 bytes). The coordinator's `writeJSON` (`internal/api/handlers.go`) uses `json.NewEncoder` with HTML escaping enabled by default. A legal task payload of up to `executor.MaxPayloadSizeBytes` (64 KiB) containing characters like '<', '>', or '&' is re-encoded as 6-byte escape sequences (`\u003c`, `\u003e`, `\u0026`), expanding up to 6x on the wire (~384 KiB). 64 KiB headroom provides ample space for the assignment JSON wrapper, task type, IDs, lease tokens, and timestamp metadata while strictly bounding memory growth on adversarial streams.
- Scope addition (null assignment check on HTTP 200): In `origin/main:internal/worker/client.go` func `pollWork`, the base code decoded `res.Assignment` and returned `(res.Assignment, nil)`. For an HTTP 200 response with null assignment (e.g. `{"assignment": null}` or `{}`), `pollWork` returned `(*coordinator.WorkAssignment(nil), nil)`. Downstream in func `(a *Agent) Run` (the polling loop), the code checked `if assignment == nil { time.Sleep(baseBackoff); continue }`, resetting `consecutiveFailures` to 0 and sleeping `baseBackoff` before retrying silently. P4-10 adds an explicit check in `pollWork` rejecting an empty assignment on HTTP 200 with typed error "poll returned 200 OK without an assignment", which downstream in `Run` records a poll error, increments `consecutiveFailures`, and backs off with jitter. Guarded by `TestPollWork_NullAssignmentRejected` and mutation M6.
- Zero line numbers in live documentation: In accordance with repository documentation rules, all references in live docs cite function names (e.g. `pollWork`, `renewOnce`, `reportResult`) rather than line numbers.

## Security review
- Assumptions challenged:
  - Coordinator poll responses can be trusted to be finite: Challenged and rejected. An attacker or corrupted coordinator streaming infinite bytes or an oversized envelope could exhaust worker memory. Solved by bounding responses via `io.LimitReader` and `MaxPollResponseBytes = 448 KiB (458,752 bytes)`.
  - JobID and AttemptID are always benign URL path segments: Challenged and rejected. Special characters (`../`, `?`, `#`, `%2f`) alter URL structure and path hierarchy if interpolated directly. Solved by escaping with `url.PathEscape`.
- Attacks tried:
  - Streaming oversized response body (>458,752 bytes) during work polling on HTTP 200 (assignment) and HTTP 503 (error envelope): Executed, confirmed bounded to `MaxPollResponseBytes`.
  - Wire expansion attack via HTML escaping of 64 KiB legal payload containing `<`: Executed, confirmed decoded intact without truncation.
  - HTTP 200 OK with null assignment: Executed, confirmed rejected with explicit error.
  - URL path traversal via `"../"`, path truncation via `"?"` and `"#"`, and percent-encoding ambiguity via `"%2f"`: Executed, confirmed preserved and escaped as single path segments.
- Not tested:
  - Network-layer TCP packet fragmentation across multiple physical machines (deferred to V3).
- Findings:
  - SEC-060: Fixed (executed).
  - SEC-061: Fixed (executed).
