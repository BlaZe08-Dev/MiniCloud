## Security review
Assumptions challenged:
- The new poll fields carry no client input: `policy` and `fallback_reason` are coordinator constants (confirmed by code reading). Their exact values per path are pinned by `TestAPI_Poll_PolicyFieldOnWire`, `TestConformance_ClaimPolicy_PerArm` and `TestConformance_PollResponse_PolicyField`.
- The job view does not leak internal state: `assigned_at` is absent (`TestAPI_Job_AssignmentFieldsAreAdditive`, `TestConformance_JobView_AssignmentFields`; mutant E06). `last_poll_at` is on the worker, tagged `json:"-"`, and is not part of the job view (confirmed by code reading).
- Field limits: `policy` is at most 20 bytes and `fallback_reason` at most 6, both fixed strings. `assigned_worker_id` references `workers(id)` (migration 000005), and a worker ID is admitted only through `isValidIdentifier` (at most 128 characters of `[A-Za-z0-9_-]`) (confirmed by code reading). The poll body grows by under 60 bytes, inside the 64 KiB envelope headroom of `MaxPollResponseBytes` (confirmed by code reading).
- No new unauthenticated surface: no handler, route or request parsing changed (confirmed by code reading of the diff). The existing abuse and fault tests ran unchanged (`make test-security`, counts in the report).

Findings:
- **F-5c2-1, major, executed (pre-existing on main, not fixed: break before fix).** `worker.ComputeBackoffWithJitter` computes `1 << (failureCount - 1)`. From 64 consecutive failures on, the shift overflows and the backoff is 0 s (`P4-08e-evidence/probe-backoff-overflow.log`: failures 63 gives 1.78 s, while 64, 65, 100 and 301 each give 0 s). `Agent.Run` counts consecutive poll failures without a bound, so after 64 failed polls in a coordinator or database outage (roughly 2.5 minutes of backoffs, inferred from the 1.5 s to 3 s range) the worker polls with no sleep: a hot loop against a struggling coordinator from every worker at once. The renewal and delivery retry loops call the same function (confirmed by code reading); whether they reach 64 failures was not tested. INV-17's bound (no sleep above the cap) still holds; the lower side is what breaks. Suggested fix: clamp `failureCount` before the shift (the multiplier is capped at 16 anyway), plus a test that the backoff stays positive and at least half the cap for failure counts from 5 to 10,000. Not fixed because the task scope does not authorise it. The register entry is for the owner of `docs/security/findings.md`.
- **For the findings register, informational, inferred.** The job view now names the worker holding a reservation. Any client can already list worker IDs (`GET /v1/workers`) and poll as any worker (SEC-004, accepted; ADR-0017 Section 6.2, "A worker polls on behalf of another worker ID"). The field makes a target easier to pick, but adds no capability. Same root cause as SEC-004.

Not tested: a PostgreSQL-backed HTTP test of the poll body (the coordinator copies the repository's values, which the shared cases pin per backend); worker IDs at the 128-character limit in the job view; an old worker against this coordinator (the worker decodes by field name, confirmed by code reading).
