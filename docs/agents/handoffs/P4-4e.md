## 2. Design of the harness and the fault proxy (executed, `tests/internal/sectest`)

* **Schema isolation**: every database test creates a random schema in the per-worktree test database (`minicloud_claude_test`), migrates it, drops it on cleanup. Name guards: the database name must end in `_test` and `minicloud_test` (shared) is refused outright. Tests skip cleanly when `MINICLOUD_TEST_DATABASE_URL` is unset.
* **Fault proxy** (`proxy.go`): in-test TCP proxy with modes forward, drop (close live and new connections), reset (RST via `SO_LINGER=0`), blackhole (accepts and swallows, never answers: half-open), delay (fixed latency per direction). Used between the coordinator and only the test database (outage) and between a real worker and a real coordinator (partition). `TestFault_ProxySelfTest` proves each mode behaves as the outage tests assume. The shared `minicloud-postgres` container was never stopped, started or restarted; `MINICLOUD_ALLOW_CONTAINER_RESTART` and `MINICLOUD_CONFIRM_CONTAINER` were never set; `make test-outage` was never run (`docker ps` after the runs: container up 8 hours, healthy).
* **Rig** (`rig.go`): the real `api` handler, `coordinator.Service` and repository in-process behind `httptest`. Memory rigs run on a `FakeClock`; PostgreSQL rigs use database time, so lease expiry is produced by an `UPDATE attempts SET lease_expires_at` on the isolated schema and retry backoff by moving `not_before` (test-side actions, labelled in the code).
* **Real binaries** (`proc.go`): coordinator, worker and mc are built once into a private temporary directory; ports are claimed from 18080 upward with an `flock`; children get exactly the environment given (nothing inherited); every PID is recorded and only recorded PIDs are killed; `TestMain` in both packages kills and fails on leftovers. After all runs: no MiniCloud process and no build directory remained (`P4-4e-evidence/ps-after.txt`).
* **Invariant checker** (`invariants.go`): attempt numbers 1..n, attempts at most max_attempts, at most one active attempt per job, none on a terminal job, a RUNNING job has exactly one, at most one result row, SUCCEEDED has one, no worker above its slots; on PostgreSQL also two atomic queries.
* **Sleeps**: every remaining `time.Sleep` is either a bounded-poll interval or sits next to a comment giving its reason (fault latency, justification of a short settle before an assertion that does not depend on its length, or the timeout under test).

### 5.1 Oversize output end to end with the real worker (fix round, item A; executed)

**Executors and caps (confirmed by code reading).** Three executors exist, registered by `NewRegistry` in `internal/executor/executor.go`: `EchoTask` (`internal/executor/echo.go`), `SleepTask` (`sleep.go`) and `SHA256LoopTask` (`sha256_loop.go`). `Sleep` and `SHA256Loop` return a short fixed JSON object and cannot exceed the limit. `Echo` re-encodes the payload and adds 9 bytes, so a payload near 64 KiB can. The only cap was in `Registry.Execute`, on the success path, as a byte slice at `MaxOutputSizeBytes` with no marker; on the failure path the output was returned as is, and the error text (`err.Error()` in `ExecuteAndReport`) was never bounded in the worker. The coordinator enforces the limits in `CommitAttempt` of both repositories and answers 400 `OUTPUT_TOO_LARGE` (output) or 400 `INVALID_REQUEST` (error text).

**Worker behaviour on a 4xx.** `deliverResult` calls `ReportResult` and stops at the first terminal rejection: `isTerminalDelivery` treats 403, 404, 409 and a plain 400 as final. So after one 400 the worker logs `coordinator permanently rejected result (non-retryable)` and returns. `ExecuteAndReport` then returns, and its deferred `stopRenew` ends the renewal goroutine, so no lease renewal runs after the rejection and none is needed for delivery (one request per attempt).

**Observation (real worker agent, real coordinator handler, both backends, built-in `echo`, red run on the code before the fix).** Payload of 65,535 bytes: `{"m":"` + 65,227 `a` + 100 `€` + `"}`; echo output 65,544 bytes; cut at 65,536 inside a `€`. Saved in `fix-A-red-builtin-echo.txt` (timestamps are test time since the job was queued; the test forces lease expiry once an attempt has stayed RUNNING with no result for 1.2 s, instead of waiting for the 30 s lease, then runs one sweeper tick and moves the retry backoff):

* PostgreSQL: T+0.25 s attempt 1 RUNNING; the worker's result is rejected with 400; T+1.54 s stuck, lease expired, T+1.76 s attempt 1 LOST and job RETRYING; attempt 2 RUNNING at T+2.40 s, rejected, LOST at T+3.80 s; attempt 3 RUNNING at T+5.11 s, rejected, LOST; T+6.42 s job FAILED with attempts LOST, LOST, LOST, 0 result rows. Memory backend: same sequence, FAILED at T+6.48 s.
* All three attempts carry error class LEASE_EXPIRED and the text `lease expired: worker failed to renew`; the real cause (a rejected result) is only in the worker log. The classification and the retry budget are spent on a failure that no retry can change.
* With the default 30 s lease the same sequence would take at least 3 x 30 s plus two retry backoffs (inferred from the lease and backoff settings, not run).

Outcome (i): a poison loop that burns every attempt with no result stored, reachable by any caller with the built-in `echo` task (SEC-004 applies; no authentication). The two test-executor variants (100 KiB output plus 40 KiB error text on a failing task; 100 KiB plain ASCII on success) show the failure path the same way for the error case (`fix-A-red-first-run-errorpath-ascii.txt`); the plain ASCII success case was already capped and ended SUCCEEDED in the red run.

**After the fix** (`fix-A-green.txt`, both backends): built-in echo ends SUCCEEDED at T+0.10 s (memory) and T+0.36 s (PostgreSQL) with 1 attempt COMPLETED, 1 result row and an output of 65,535 bytes ending in the marker; the failing task ends FAILED after 1 attempt with output cut to 65,536 and error text cut to the 10 KiB limit, both marked; plain ASCII ends SUCCEEDED with exactly 65,536 bytes. The marker is `\n[truncated]`.

Mutation proofs of the fix are M21 and M22 in section 6.
