## 2. Harness design (planned)

* `tests/internal/sectest` (planned package, helpers only): per-test PostgreSQL schema isolation with the P4-T1
  name guards (database name must end in `_test`, refuses `minicloud_test`), a **TCP fault proxy**, a process runner
  for real binaries, a backend matrix (in-memory always, PostgreSQL when `MINICLOUD_TEST_DATABASE_URL` is set), an
  invariant checker that reads the database (or the API for memory).
* **Fault proxy** (planned): listens on `127.0.0.1:0`, forwards to one upstream. Modes switchable at runtime:
  `forward`, `drop` (close every live connection and refuse new ones by closing at accept), `reset` (close with
  `SO_LINGER=0` so the peer sees RST), `blackhole`/half-open (accept and read, never forward, never answer),
  `delay` (add a fixed latency per direction). Used (a) between the coordinator and **only** the per-worktree test
  database to simulate a database outage, and (b) between a real worker process and a real coordinator process to
  simulate a network partition. The shared `minicloud-postgres` container is never stopped, started or restarted;
  `MINICLOUD_ALLOW_CONTAINER_RESTART` and `MINICLOUD_CONFIRM_CONTAINER` are never set; `make test-outage` is never run.
* **Real binaries** (planned): coordinator, worker and mc are built into `t.TempDir()`; listen port chosen free from
  18080 upward; every started PID is recorded and only recorded PIDs are killed; every wait is a bounded poll; a
  `ps` check after the run proves no process outlives it.
* **Time**: in-memory scenarios use `workertest.FakeClock` and `storage.WithClock`. PostgreSQL uses database time, so
  lease expiry is made by an `UPDATE attempts SET lease_expires_at` on the test schema (a test-side action, labelled in
  each test), or by a short real lease with bounded polling for the real-binary tests. Each remaining sleep gets a
  comment that justifies it.

### Stage 4 additions (real binaries, background loops, ambiguous commit; all executed)

Real-binary results (raw: `P4-4e-evidence/realproc-run1.txt`, `realproc-run2.txt`; every PID recorded, `TestMain` proves none outlives the run):
* `TestFault_WorkerKill9_LeaseSweepAndRetry` PASS (10 s): attempt 1 `LOST` on the killed worker, `LEASE_EXPIRED` and `JOB_RETRYING` once each, attempt 2 `COMPLETED` on the survivor, one result row.
* `TestFault_WorkerPartition_ProxyBlackhole_ZombieAbortsAndLateCommit409` PASS (15 s): partition swept attempt 1 to `LOST`; after healing the zombie sent no result (0 `DIAGNOSTIC_LATE_RESULT` events), attempt 2 finished the job. This closes 4c-b A2 end to end with real binaries.
* `TestFault_CoordinatorKill9_StartupGrace_SurvivingCommit` PASS: within grace the commit returns 200; the control (grace over, attempt reaped) returns 409.
* `TestFault_CoordinatorKill9_DuringCommitStorm_InvariantsAfterRestart` PASS: 120 `sleep` jobs through 3 real workers, coordinator `kill -9` with attempts in flight (the test fails if none were), restart on the same schema, all jobs `SUCCEEDED`, invariants hold, worker capacity back to full. The kill point is random (seed logged).

Findings of this stage:
* **F-4e-3 (Low, executed, accepted by the orchestrator as a documented limit)**: after a half-open partition heals, recovery takes up to about 15 s when every pool connection was held by a hung request (measured 15.07 s, pool of 2; 14.73 s, pool of 4). Cause: pgx closes a cancelled half-open connection asynchronously with a hard-coded 15 s deadline (`asyncClose` in pgconn) and the slot is unusable until then. No MiniCloud setting governs it. Meanwhile users see 503 `SERVICE_UNAVAILABLE` with `Retry-After: 1`; there is no corruption (invariants checked). Test `TestFault_DBOutage_HalfOpen_RecoveryTime`.
* **F-4e-4 (Informational, executed)**: graceful shutdown of the real coordinator with a half-open database and a hung request took 17.1 s after SIGTERM. Bounded (server shutdown 10 s limit plus the pgx close), not unbounded, so no red test. `TestFault_CoordinatorShutdown_HalfOpenDatabase_Bounded`, `P4-4e-evidence/shutdown-halfopen.txt`.
* **F-4e-5 (High, executed, FIXED)**: the lease sweeper loop and the worker reaper loop had no deadline, so one half-open database connection parked them for good: after the partition healed the sweeper completed no further sweep for 60 s (stuck at 3), so crashed workers' attempts would never be reaped until a coordinator restart. Red: `P4-4e-evidence/F-4e-5-red.txt` (sweeper) and `P4-4e-evidence/F-4e-5-reaper-red.txt` (reaper, fix reverted for the reaper only). Fix: `BackgroundCallTimeout` (8 s) in `internal/coordinator/service.go`, a per-iteration deadline in `StartReaper` (`internal/coordinator/service.go`) and in `LeaseSweeper.Run` (`internal/coordinator/sweeper.go`). A timed-out tick is a failed tick, so the existing outage grace window opens afterwards. Green: `P4-4e-evidence/F-4e-5-green.txt` (3 sweeps and 3 reaps resumed 6.6 s after healing). Test `TestFault_Sweeper_ResumesAfterHalfOpenDatabase`.
* **F-4e-6 (Informational design observation, executed)**: the service holds one mutex across database calls in `PollWork` and `CommitResult`, so one hung call serialises every poll and commit behind it until the request deadline. Measured with the database half-open (`TestFault_DBOutage_HalfOpen_OtherRequestsNotStalled`): healthz 200 in 0 ms; hung poll, queued poll, queued commit, get and heartbeat all 503 in 8.01 s, none later. The stall is bounded by the 8 s deadline; it is not a deadlock.
* **F-4e-7 (Informational performance observation, executed)**: a work poll costs 20 client-to-database flights, an empty poll 4, a submit 5 (counted at the fault proxy by `ClientChunks` during `TestFault_PollCost_DatabaseRoundTrips`, `P4-4e-evidence/poll-cost.txt`; cross-check: 2.066 s at 100 ms round trips in `deadline-and-stall.txt`). Relevant to the V2 dispatch benchmark and to the deadline limit (a database with more than about 400 ms round trip would cut off polls).

Ambiguous commit: `TestFault_AmbiguousCommit_ReplayIsSafe` (memory and PostgreSQL) PASS. When the deadline fires after the commit applied, the caller sees 503, the stored job is already `SUCCEEDED` (or `FAILED` for a failure commit), the replay with the same token returns the documented 409 `JOB_ALREADY_TERMINAL`, one result row, one attempt, nothing overwritten. I did not receive the earlier orchestrator message that asked for "the stored success must be returned" on replay; the protocol (6.3, D-R3-02) documents 409 and names a 200 replay as a possible future change, so asserting 200 would require a protocol change. Decision for the orchestrator below.

Decisions recorded: (1) `RequestTimeout` stays a hard-coded 8 s for V1; no `MINICLOUD_REQUEST_TIMEOUT`; it becomes a V3 item when remote databases are in scope (orchestrator decision). (2) F-4e-3 accepted as a documented Low limit.

### Stage 3b additions (orchestrator follow-ups 1 to 4, executed)

* Follow-up 1, request deadline: `TestFault_RequestDeadline_NoLegitimateRequestCutOff` walks every endpoint through a database with 100 ms round trips. Slowest legitimate request: 2.107 s (work poll and a 64 KiB-output commit). No endpoint long-polls: an empty poll answers 204 in 4 ms. `RequestTimeout` 8 s stays below the 10 s server write timeout. Limit observed: at 600 ms round trips a work poll (about 20 round trips) exceeds 8 s and is cut off with 503; that is a database far slower than any V1 deployment (127.0.0.1). Recommendation for the orchestrator: make the value a config (`MINICLOUD_REQUEST_TIMEOUT`) only if remote databases are in scope; not added. Raw output: `P4-4e-evidence/deadline-and-stall.txt`.

Recovery after the proxy healed took 23 to 115 ms; the extra 15 s was `pgxpool.Close` at test teardown waiting on a half-open connection, now avoided by severing in the proxy first. The half-open test takes 8.4 s (dominated by the 8 s deadline).
