## Findings

**F-R1: minor. Test isolation: the pass advisory key is per database, so two test processes on one database break each other's passes.**
- Location: `AssignmentPassLockID` in `internal/storage/postgres/assignment.go`, and `setupTestPool` (one schema per test, one database per worktree).
- Evidence label: executed (mechanism and gate run 1); inferred (which process held the key in run 1).
- Evidence:
  - Probe `audit_advisory_scope_test.go.txt` (function `Audit_AdvisoryKey_IsDatabaseWideAcrossSchemas`). A connection in test schema B holds the key, and a pass in test schema A of the same database returns `{Skipped:true ...}`. After the release, the pass runs.
  - Gate run 1 of `make test-db` failed 4 assignment tests with exactly that symptom (`control: pass after release: res={Skipped:true ...}`, `control: job was not reserved`). Run 2, alone on the database, passed 131/0/0.
  - A second `make test-db` in this worktree, on `minicloud_claude_test`, was observed starting at 21:59:36 from a desktop terminal.
  - Run 1's failing tests ran 15 to 18 s into a package run that ended at 21:59:42 and took 115.8 s. That process therefore does not explain them by itself, and I did not identify the holder.
- Impact: production is unaffected; one key per database is the intended cross-coordinator guard (Section 4.2). But `make test-db` turns red whenever anything else runs a pass on the same database. That is a false red, and an owner or agent who re-runs it may wrongly blame the code.
- Suggested fix (for the orchestrator): a test-only option for the key (for example a repository option the PostgreSQL test helpers set per schema), or a documented rule that one test database takes one `make test-db` at a time.

**F-R4: major. INV-5 (rotation persisted per type) is not guarded on the cursor update path. Mutant A01 survives all 48 assignment tests.**
- Location: the `assignment_cursor` upsert in `AssignQueuedJobs` (`internal/storage/postgres/assignment.go`), and its test `TestPostgresRepository_AssignmentCursor_SurvivesRestart`.
- Evidence label: executed.
- Evidence:
  - A01 makes the upsert keep the old `last_worker_id` on conflict. Red is 48 PASS and 0 FAIL (`audit-mut-A01-red.log`).
  - The builder's INV-5 test runs only two passes per type, so it exercises only the first INSERT of each cursor row, never the UPDATE. (P03, "ignore the stored cursor", is a different mutant.)
- Impact of the escaped defect: after the first decision for a type, every pass restarts from the first worker ever chosen. With workers a, b and c continuously eligible: pass 1 picks a, pass 2 picks b, and pass 3 picks b again while c waits. That violates S1 (Section 2.6), across passes and across restarts. The production code is correct today; nothing would catch a regression.
- Suggested fix: adopt `Audit_Cursor_UpdatePathPersistsAcrossPasses` (three passes, a restart before the third, the stored row checked after each pass) or an equivalent test, with its mutation proof against A01.

**F-R5: minor. The in-pass cursor advance has no guard on the `cursor_before` audit field. A01b survives.**
- Evidence label: executed.
- Evidence: red is 48 PASS (`audit-mut-A01b-red.log`). Selection is unaffected, because a reserved worker leaves E(t), so the successor of the stale cursor is the same worker. The persisted cursor is also unaffected. Only `cursor_before` in `JOB_ASSIGNED` is wrong for the second and later decisions of a type within one pass. The Blueprint audit trail ("structured audit logs for every decision", Section 2.1) then records a false input.
- Suggested fix: adopt `Audit_Event_CursorBeforeAdvancesWithinPass`, or assert `cursor_before` in an existing case.

**F-R6: minor. The fallback arm's "no live reservation" bound has no guard. A06b survives.**
- Evidence label: executed.

- Suggested fix: adopt `Audit_Fallback_ExpiredUnrevokedReservationIsClaimable`.
