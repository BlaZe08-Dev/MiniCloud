## Findings

### R-01 (major) SEC-022 leaks a worker slot permanently; severity and evidence label are wrong
- Location: `docs/security/findings.md:34` (register row), `docs/security/findings.md:296-324`
  (entry), `docs/security/threat-model.md` item 12.
- Evidence label: **executed** (E1), plus **confirmed by code reading**.
- Evidence: `TestReviewP400_SEC022_DoubleCancelLeaksWorkerSlot` (`tests/review/sec022_probe_test.go`)
  runs over HTTP against the in-memory and PostgreSQL coordinators. The steps are: register a 1-slot
  worker, poll a job, cancel it twice, then send the worker's commit. The commit gets HTTP 409
  `JOB_ALREADY_TERMINAL`. The job is then `CANCELLED` while its attempt is still `RUNNING`.
  `available_slots` is 0, and in PostgreSQL the SQL check reports
  `worker_capacity.available_slots=0, active attempts on terminal jobs=1`. The next poll by the now
  idle worker returns `HTTP 503 NO_WORKERS_AVAILABLE`. Both subtests FAIL with
  `INVARIANT VIOLATION ... still RUNNING` and `SLOT LEAK`.
  Root cause: both `CommitAttempt` implementations return `ErrJobAlreadyTerminal` before they touch
  the attempt (`internal/storage/postgres/repository.go:983-984` returns, and the transaction rolls
  back; `internal/storage/inmemory.go:577-579`). Nothing else closes the attempt. The heartbeat
  reaper only marks workers (`internal/coordinator/service.go:320-333`). `worker_capacity` counts
  `PENDING`/`RUNNING` attempts (migration 000002), so the slot never comes back. Re-registering
  does not touch attempts.
  Impact: every slot in the fleet can be exhausted by anyone who can reach the API. Two
  `POST /v1/jobs/{id}/cancel` calls per running job are enough, with no credentials (SEC-004). In
  PostgreSQL mode the leak is durable across coordinator restarts. It also violates
  `docs/fault-injection-plan.md:141` (invariant 4). `TestPostgresRepository_Concurrency_MixedOperationsStress`
  cancels running jobs at random but never checks that invariant
  (`internal/storage/postgres/concurrency_test.go:450-513`), which is why it never caught this.
- Suggested fix: rate SEC-022 at least **Medium**, status "Open (executed)", and cite the probe and
  E1. Rewrite Impact to state the slot leak and the denial of service. Because the rating becomes
  Medium, use the full structured format. Record in the design that the Slice 4a fix must also
  cover the leaked state: either `CommitAttempt` on a terminal job closes the attempt, or the
  sweeper does (R-02). Rows already leaked before 000004 need a cleanup statement or a sweeper rule.
  Add invariant 4 to the mixed-operations stress test and to the planned conformance tests. The
  builder may cherry-pick the probe as the SEC-022 regression test and drop its env gate when the
  fix lands.

### R-02 (major) Sweeper rule for an attempt whose job is already terminal is undefined
- Location: `docs/adr/0014-lease-model-and-expiry.md:136-143`, `docs/schema.md:379-381`,
  `docs/adr/0016-cancellation-semantics.md:126`.
- Evidence label: **inferred** from the documented algorithm and **confirmed by code reading** of
  the FSM (`internal/domain/transition.go:5-33`, terminal states have no exits).
- Evidence: the job branch covers only `CANCEL_REQUESTED`, retry, and exhausted. A `RUNNING`
  attempt on a `CANCELLED` job (R-01) matches the candidate scan. 000004 makes this certain for
  existing rows, because it gives them `lease_expires_at` = migration time + 30 s
  (`docs/schema.md:298-300`). The sweeper would then attempt `CANCELLED -> RETRYING` or `-> FAILED`,
  which the FSM rejects. The scan is `ORDER BY lease_expires_at ASC LIMIT 50`, so these poison rows
  stay at the head of every batch. The CANCEL_REQUESTED case also says "`LOST` (or `CANCELLED`)" for
  the attempt in two places, which leaves the attempt state undecided.
- Suggested fix: add a branch. If the job is terminal, set the attempt to one named state, leave
  the job unchanged, and write one event. Choose one attempt state for the CANCEL_REQUESTED case.
  Add both as conformance cases.

### R-03 (major) `error_class` values contradict each other and the proposed CHECK
- Location: `docs/adr/0015-retry-policy-and-failure-classification.md:81`, `docs/schema.md:308-312`,
  `docs/protocol.md` section 6.2 ("Allowed `error_classification` values").
- Evidence label: **executed** (E5) and **confirmed by code reading**.
- Evidence: ADR-0015 says the sweeper writes `"INFRASTRUCTURE_FAULT"` (or `"LEASE_EXPIRED"`) and
  also mentions `"TRANSIENT"`. The proposed `chk_attempts_error_class` allows only `PERMANENT`,
  `RETRYABLE` and `UNKNOWN`. A sweeper insert as written would fail with SQLSTATE 23514, so the
  sweep would never succeed. The existing migrations have no `error_class` column and no constraint
  on it (E5), so the column and its CHECK both arrive in 000004. ADR-0015 also says the "job failure
  summary" records `error_class`, but `jobs` has no such column.
- Suggested fix: publish one enumerated list, for example `PERMANENT`, `RETRYABLE`, `UNKNOWN`,
  `LEASE_EXPIRED`. Say which writer may set each value (worker report or sweeper only), use the
  same list in the 000004 CHECK and in protocol 6.2, drop `TRANSIENT` and `INFRASTRUCTURE_FAULT`,
  and name where the job-level value lives (the `job_events` details).

### R-04 (major) Two 409 codes for one condition; check order and late-result recording unspecified
- Location: `docs/adr/0014-lease-model-and-expiry.md:85,95,204`; `docs/protocol.md:395-405` and
  `docs/protocol.md:466`; `docs/phase4-plan.md:11,89,123`; `docs/failure-model.md` FS-03 and FS-04;
  `docs/state-machine.md:182`; `docs/protocol.md:454-455`.
- Evidence label: **confirmed by code reading**.
- Evidence: the docs name the swept-attempt condition `LEASE_EXPIRED` in some places,
  `STALE_ATTEMPT_REJECTED` in others, and "`ErrStaleAttempt`, HTTP 409 `LEASE_EXPIRED`" in FS-04.
  Today the handlers emit only `STALE_ATTEMPT_REJECTED` (for `ErrStaleAttempt`) and
  `JOB_ALREADY_TERMINAL` (`internal/api/handlers.go:125-128`). The worker keys on the status code
  alone (`internal/worker/client.go:268-270`), so every 409 is already terminal for the worker, and
  `TestIsNonRetryableReportError` pins that (`internal/worker/client_test.go:25`). Protocol 6.3 adds
  `ATTEMPT_NOT_RUNNING` and `JOB_CANCELLED`, which no other section uses. Check order matters:
  `CommitAttempt` checks the job state before the attempt state
  (`internal/storage/postgres/repository.go:983-988`). A late commit after the sweeper has already
  failed or cancelled the job therefore gets `JOB_ALREADY_TERMINAL`, not `LEASE_EXPIRED`. Nothing
  says whether `diagnostic_late_result` is written on that path. Today any rejection rolls the whole
  transaction back, so an event written in the same transaction would be lost.
- Suggested fix: add one table to protocol.md that maps condition to HTTP status, code, domain
  error, and whether a diagnostic event is written. The conditions are: attempt `LOST`/`TIMED_OUT`,
  attempt superseded, token mismatch, worker mismatch, job terminal, and attempt or job not found.
  Fix the check order. Delete the unused codes or assign them. Say that the diagnostic event is
  committed in its own transaction, written once per attempt (see R-17).

### R-05 (major) In-memory retry dispatch: the docs contradict each other, and the default mode would strand RETRYING jobs
- Location: `docs/adr/0015-retry-policy-and-failure-classification.md:120-122` against
  `docs/phase4-plan.md:48` and `docs/phase4-plan.md:59`.
- Evidence label: **confirmed by code reading**; **executed** search (E7).
- Evidence: ADR-0015 says delayed dispatch is "Postgres-mode-only" and that in-memory covers only
  state-machine semantics. The plan requires in-memory `not_before` filtering, with a mutation
  proof. `EnqueueRetry` appears in neither code nor docs at `aa13a4c` (E7), so concern 13's premise
  that the docs introduce it no longer holds. The in-memory `DispatchNextJob` scans `jobOrder` by
  state (`internal/storage/inmemory.go:486-491`), so the Postgres predicate fits it directly with no
  re-enqueue. That is right for the repository, and it avoids a repeat of the SEC-002 drift.
  However, the default driver is `memory` (`internal/config/config.go:48`), and in that mode the
  coordinator does not call `DispatchNextJob`. It runs `queue.Claim` and then `repo.DispatchJob`
  (`internal/coordinator/service.go:401-409`). A job that enters `RETRYING` has no queue item, so it
  would never be dispatched again. Two smaller parity gaps: in-memory dispatch hard-codes the event
  `fromState` to `QUEUED` (`internal/storage/inmemory.go:437`, `internal/storage/inmemory.go:539`),
  and `CommitAttempt`/`CancelJob` use `time.Now()` rather than the injected clock
  (`internal/storage/inmemory.go:607`, `internal/storage/inmemory.go:687`).
- Suggested fix: one rule for the repository. `DispatchNextJob` and `DispatchJob` in both backends
  accept `QUEUED`, or `RETRYING` with `not_before <= now` (database time, or the injected clock),
  with no re-enqueue. For the memory coordinator, the orchestrator must choose between routing
  memory mode through repository dispatch, as `NewPostgresService` does, and specifying a delayed
  re-enqueue. The first removes the second dispatch path and is my recommendation; it does keep the
  SEC-010 unbounded-queue concern moot only for Postgres. Write the conformance test against that
  rule. Use the actual from-state in events and the injected clock in every in-memory write.

### R-08 (major) Sweeper locking: three variants, and the grace check placed twice
- Location: `docs/adr/0014-lease-model-and-expiry.md:116-127` (plain `FOR UPDATE`),
  `docs/schema.md:358-371` (`FOR UPDATE SKIP LOCKED` under a heading that says "SKIP LOCKED / NOWAIT");
  the same wording in CHANGELOG.md and `docs/PROJECT_STATE.md`. Grace:
  `docs/adr/0014-lease-model-and-expiry.md:155-163` (whole passes suppressed) against
  `docs/schema.md:377` (grace re-checked per candidate under the locks). Boundary:
  `docs/adr/0014-lease-model-and-expiry.md:134` skips when `>=` now, `docs/phase4-plan.md:87`
  skips when `>` now.
- Evidence label: **executed** (E3) for the syntax; **confirmed by code reading** for the rest.
- Evidence: PostgreSQL returns `ERROR: syntax error at or near "NOWAIT"` for `FOR UPDATE SKIP LOCKED
  NOWAIT` (E3). The two options cannot both apply to one statement. Plain `FOR UPDATE` blocks for up
  to `lock_timeout` (5 s by default: `cmd/coordinator/main.go:61-67`, `internal/config/config.go:111`)

- Suggested fix: choose `SKIP LOCKED` on all three statements, with zero rows meaning "skip, retry
  next tick", and state how a skipped lock is told apart from a missing row. Check grace once, at
  the start of the tick. Use one comparison (`lease_expires_at < clock_timestamp()` means expired)
  in every document.

### R-09 (major) Outage detection is partly unobservable and can keep the sweeper in grace indefinitely
- Location: `docs/adr/0014-lease-model-and-expiry.md:157-163`.
- Evidence label: **confirmed by code reading** (readyz) and **inferred** (timing).
- Evidence: (a) `/readyz` pings are made by outside callers. `HandleReadyz` keeps no state the
  sweeper could read (`internal/api/handlers.go:417-424`). (b) The gap rule has two thresholds
  ("`1.5 x sweeper_interval` (or > 10s)"). It fires on any tick slower than 7.5 s, and with blocking
  locks (R-08) a 50-candidate tick can exceed that without any outage. Each firing grants 30 s of
  grace, and nothing caps how often it can be re-entered, so a slow or contended database can keep
  dead workers' jobs unreclaimed indefinitely. (c) The design's own example, host suspend, is not
  caught by a Go `time.Since` gap, because Go measures elapsed time with a monotonic clock that on
  Linux does not advance during suspend (inferred from the Go `time` package documentation; not
  executed). (d) `outage_grace_until` mixes database time with in-process wall time.
- Suggested fix: measure the gap on database time. Read `clock_timestamp()` at the start of each
  tick and compare it with the previous successful tick, which also covers database pauses and
  suspend. Count only the sweeper's own failed pings as an outage, and drop `/readyz`. Exclude the
  sweeper's own work time, for example by measuring from the end of one tick to the start of the
  next. Cap consecutive grace windows, or require one completed sweep between windows. Add a
  planned test where a deliberately slow tick must not enter grace, and one where a 35 s database
  stop must.

### R-10 (major) Worker delivery loop: 404 means two opposite things, and 400 is unspecified
- Location: `docs/failure-model.md:55-68`, `docs/protocol.md:466-467`,
  `docs/adr/0014-lease-model-and-expiry.md:172`.
- Evidence label: **executed** (E2) and **confirmed by code reading**.
- Evidence: the 60 s bound (lease + grace) does outlast the 45 s FS-05B outage, and it is far
  longer than today's loop. Today's loop is five attempts, the last starting about 1.5 s after the
  first, followed by a final wasted sleep (`internal/worker/client.go:324-355`, E10). So concern 2
  holds in principle. Problems:
  1. failure-model.md lists 404 as terminal for renewal and report. Protocol 6.4 says a 404 or 405
     on `/renew` means an old coordinator, so the worker should degrade and keep running. E2 shows
     the two cases differ only in the body: the old coordinator returns
     `404 text/plain "404 page not found"`, while a real miss returns `404 application/json
     {"error":{"code":"JOB_NOT_FOUND",...}}`. A status-only rule would make a new worker keep
     running a job the coordinator no longer knows. The mux returns 404, not 405, for this route.
  2. The design names the transient statuses (500, 502, 503, 504, plus transport errors) and the
     terminal ones (403, 404, 409). 400 and other 4xx are in neither list. Today 400 is retryable
     (`internal/worker/client.go:268-270`), and `internal/worker/client_test.go:22` pins that. Under
     a 60 s loop a deterministic 400 would be retried for a minute.
  3. Pinning-test citation: `TestAgent_ReportResult_RejectionHandling` spans
     `internal/worker/client_test.go:40-112`, not the cited range (E9). `TestIsNonRetryableReportError`
     at `internal/worker/client_test.go:16-38` is correct.
  4. The design says nothing about what happens to the delivery loop and renewals on worker
     shutdown (`ctx` cancelled), or after the bound expires. Renewal must stop too.
- Suggested fix: decide on the JSON error code, not the status. A 404 without the MiniCloud error
  envelope means an old coordinator; `JOB_NOT_FOUND`/`ATTEMPT_NOT_FOUND` mean abort. Make 400
  terminal or explicitly retryable, and list the test change if it flips. Correct the line range.
  State the shutdown and expiry behaviour.

  `INVALID_REQUEST`, and 503 on outage. The status codes in protocol 3.4 otherwise match, which

  blueprint section 8, rather than calling it additive. List 400 and 503. Return a flag or the

### R-16 (minor) Worker behaviour on renewal transport errors is not specified (concern 14)
- Location: `docs/adr/0014-lease-model-and-expiry.md:52`, `docs/protocol.md` section 6.1.
- Evidence label: **confirmed by code reading** of the docs.
- Evidence: only 200, 403 and 409 are specified. Transport errors and 5xx while the task is still
  running are not.
- Suggested fix: keep running and retry renewal with capped jittered backoff until a terminal reply
  or until `timeout_seconds` expires. Do not self-abort locally in V1. Trade-off: a partitioned
  worker keeps computing after its attempt may have been swept and re-dispatched, which costs
  duplicate execution (accepted under at-least-once) and is contained by the 409 on its eventual
  commit. A local self-abort after lease + grace would save compute but discard valid work in the
  coordinator-outage case that the grace design exists to protect.
