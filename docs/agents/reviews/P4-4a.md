## 5. Attacks Attempted That Did NOT Find Issues

The following attack scenarios were executed against both in-memory and PostgreSQL storage engines under `-race`:
1. **Wrong Attempt ID on Terminal Job**: Commit naming `att_bogus` on terminal job returns HTTP 409 `JOB_ALREADY_TERMINAL`, mutates zero attempts, records zero diagnostic events.
2. **Wrong Token / Wrong Worker on Terminal Job**: Commit naming the active running attempt with a bogus token returns HTTP 409 `JOB_ALREADY_TERMINAL`, cleans the attempt to `CANCELLED`/`LOST`, sets `finished_at`, records exactly one `DIAGNOSTIC_LATE_RESULT` event, and restores worker `available_slots` to 1.
3. **Repeated Terminal Commits (10x)**: Replaying commit 10 times consecutively returns `ErrJobAlreadyTerminal` each time; exactly 1 `DIAGNOSTIC_LATE_RESULT` event is recorded (bounded by `NOT EXISTS` in PG and loop check in memory).
4. **Concurrent Cancels (50 iterations, `-race`)**: Two goroutines calling `CancelJob` simultaneously on a `RUNNING` job both observe `CANCEL_REQUESTED`. Worker slot remains held (0 available slots) until worker completes/commits. Commit transitions job to `SUCCEEDED` and restores slot to 1.
5. **Commit Racing Cancel (50 iterations, `-race`)**: One goroutine committing while another cancels. Both interleavings resolve cleanly: if commit wins, job is `SUCCEEDED` and cancel gets `ErrJobAlreadyTerminal`; if cancel wins, job enters `CANCEL_REQUESTED` and commit transitions `CANCEL_REQUESTED -> SUCCEEDED`. In all 50 iterations, job finishes in a terminal state, attempt finishes `COMPLETED`, available slots return to 1, zero slot leaks.
