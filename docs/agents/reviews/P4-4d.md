## Audit Checklist & Analysis

### 1. `domain.ResolveFailure` decision function
`domain.ResolveFailure` in `internal/domain/failure.go` serves as the centralized decision function invoked by both `InMemoryRepository.CommitAttempt` and `postgres.Repository.CommitAttempt`.
- **Decision Matrix Verification**:
  - `job == StateCancelRequested`: Returns `JobState: StateCancelled, Retry: false, Exhausted: false` for all error classes and attempt counts. Cancel strictly wins over retries [confirmed by code reading].
  - `class == ClassPermanent`: Returns `JobState: StateFailed, Retry: false, Exhausted: false` immediately without retrying [confirmed by code reading].
  - `class == ClassTransient` or `ClassUnknown`, `attemptNo < maxAttempts`: Returns `JobState: StateRetrying, Retry: true, Exhausted: false`. `ClassUnknown` defaults to retryable behavior per ADR-0015 [confirmed by code reading].
  - `class == ClassTransient` or `ClassUnknown`, `attemptNo >= maxAttempts`: Returns `JobState: StateFailed, Retry: false, Exhausted: true` [confirmed by code reading].
- **Boundary Analysis**:
  - `attemptNo == maxAttempts`: Evaluates `attemptNo < maxAttempts` as false, transitioning the job to `FAILED` with `Exhausted: true` [confirmed by code reading].
  - `maxAttempts == 1`: Attempt 1 fails, `1 < 1` is false, transitioning the job to `FAILED` on first failure [confirmed by code reading].
  - `maxAttempts == 20`: Attempt 19 retries (`19 < 20`), while attempt 20 fails with budget exhaustion [confirmed by code reading].
  - `LOST` attempts: Swept attempts are stored in `attempts` and advance `attempt_no`. Subsequent attempts receive the incremented attempt number, ensuring lost attempts consume the attempt budget uniformly [confirmed by code reading].
- **Repository Agreement**:
  Both in-memory and PostgreSQL `CommitAttempt` invoke `domain.NormalizeWorkerErrorClass`, call `domain.ResolveFailure`, validate transition via `domain.ValidateJobTransition`, and record identical event types (`JobEventCompleted`, `JobEventRetrying`, `JobEventCancelled`, `JobEventFailed`) with matching `details` payloads [confirmed by code reading; executed in conformance tests].

### 2. Backoff calculation and persistence
- `domain.ComputeBackoff` in `internal/domain/retry.go` implements ADR-0015 exponential backoff (`min(30s, 1s * 2^(attempt-1)) * jitter`) with jitter in [0.5, 1.5] [confirmed by code reading].
- The coordinator `Service` maintains a single shared random source (`sweepRand`) and binds it via `retryBackoffLocked()`. Both the result commit path and the lease sweeper share this single function; no duplicate backoff implementation exists [confirmed by code reading].
- `not_before` calculation occurs exactly once per retry in `CommitAttempt` (`now.Add(delay)`), persisted to `jobs.not_before` and recorded in the `JOB_RETRYING` event details [confirmed by code reading].
- Injected randomness is verified via `SetSweepRandom` in `internal/coordinator/retry_test.go` func `TestCoordinator_RetryBackoffWithJitter` [confirmed by code reading].
- The sweeper path in `internal/coordinator/sweeper.go` func `runOnce` remains unchanged, passing `s.retryBackoffLocked()` to `repo.SweepExpiredLeases` [confirmed by code reading].

### 3. Failure classification & coordinator validation
- Worker classification in `internal/executor/classify.go` func `Classify` categorizes validation errors (`ErrInvalidRequest`, `ErrUnknownTaskType`, `ErrPayloadTooLarge`) as `PERMANENT`, execution timeouts (`ErrTaskTimeout`, `context.DeadlineExceeded`) as `TRANSIENT`, and other errors (including cooperative cancellation `context.Canceled`) as `UNKNOWN` [confirmed by code reading].
- Coordinator validation in `domain.NormalizeWorkerErrorClass`:
  - `LEASE_EXPIRED` from a worker is rejected with `ErrInvalidRequest` (HTTP 400) [confirmed by code reading; executed in `TestAPI_ReportResult_ErrorClassification`].
  - Unknown/unrecognized class strings, empty strings on failure (defaults to `UNKNOWN`), and oversized class strings are rejected with HTTP 400 without echoing the invalid string in the error message [confirmed by code reading].
  - An error class submitted with a success (`exit_code == 0 && error == ""`) is rejected with HTTP 400 [confirmed by code reading; executed in `TestAPI_ReportResult_ErrorClassification`].
- Rejection occurs prior to repository writes in `Service.CommitResult` and inside the database transaction before mutations in `postgres.Repository.CommitAttempt`, preventing partial writes [confirmed by code reading].

### 4. Cancel-wins semantics & results storage
- When a failure is committed on a job in `CANCEL_REQUESTED`:
  - Job transitions to `CANCELLED` and is never retried [confirmed by code reading; executed in smoke test and conformance tests].
  - `JobEventCancelled` event is recorded [confirmed by code reading].
  - Storing a row in `results` table records the worker outcome durably without violating ADR-0016 or protocol specification [confirmed by code reading].
- When a success arrives for a job in `CANCEL_REQUESTED`:
  - Success wins per ADR-0016 Section 5 Race 1 and protocol section 6.3: attempt transitions to `COMPLETED`, job transitions to `SUCCEEDED`, and `JobEventCompleted` is recorded [confirmed by code reading].
