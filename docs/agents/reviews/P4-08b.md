## B. Adversarial code reading (summary; findings in E)

Each line below names the hazard the audit prompt lists, what I found, and the evidence label.

- Cursor wrap or skipped worker: `NextAfterCursor` sorts a copy and takes the first ID above the cursor, otherwise the first ID. Audit mutations A02 (`>=`) and A03 (no wrap) are killed by the property tests. No issue. Executed.
- State shared across task types: `CursorSet` is keyed by task type, and `Select` reads and writes only that key. M07 is killed. No issue. Confirmed by code reading.
- A reservation that survives cancel, a terminal state, or an unhealthy worker: `CancelJob` clears on `QUEUED` and `RETRYING`; `claimLocked` clears; the revoke step clears for a holder that is missing or not `HEALTHY`. The concurrent stress test (Section D) checks the shape invariant on every job across 60 seeded runs and found none. No issue. Executed.
- A claim that ignores the accept window or worker identity: the own arm needs `AssignedWorkerID == workerID` and `AssignmentExpiresAt.After(now)`, and the fallback loop skips live reservations of any worker. M03 and M04 cover this. The exact-expiry boundary is untested (F-5a-5).
- Lapse counting during grace or for unhealthy workers: grace is not wired in 5a (disclosed, 5c). For an unhealthy holder the revoke branch does not count a lapse, which is correct, but untested (F-5a-4).
- A job at the lapse limit staying in round-robin: excluded at two sites (the type list and the candidate list). Correct, but a single-site mutation of the candidate filter survives (F-5a-3).
- Age arm opening without pass silence: `passSilent` gates it; M18 and audit A18 (heartbeat write removed) are killed. No issue.
- Refresh not single-flight or not rate-limited: the code is correct under `s.mu`. A19 (no retry after a failure) is killed. The single-flight test is white-box only (F-5a-17). The staleness threshold of 2 × interval is untested (F-5a-12).
- Zero `time.Time` or nil pointers: a zero `passCompletedAt` reads as silent and stale, which is the intended restart case. `time.Time.Sub` saturates, so `now.Sub(time.Time{})` cannot overflow. Every pointer dereference in the new code is nil-guarded. Zero-value **settings**, however, are a real hazard (F-5a-1).
- Map iteration order: `eligibleWorkersLocked` iterates `r.workers` and then sorts. Types come from `jobOrder`. Results are deterministic. The sort's effect on the event payload is untested (F-5a-7).
- Lock order: `passMu` is taken only in `AssignQueuedJobs`, before `r.mu`; the service order is `s.mu`, then `passMu`, then `r.mu`, and no path takes them in reverse. Confirmed by code reading (grep of every `Lock` site).
- fifo_pull behaviour changes: only the three diff lines in A11, which do nothing when the assignment columns are empty, plus the additive `"policy":"fifo_pull"`. A16 is killed. No issue.
- Config combinations that pass validation but violate A1: A1 is checked directly. I found no passing combination that violates it. The equality edge of the first A1 rule is untested (F-5a-10), and malformed values bypass validation (F-5a-8).

## E. Findings

### F-5a-1 (major): zero-value AssignmentSettings silently turn round_robin into first-poller-wins
- Location: `internal/coordinator/assignment.go`, `SetDispatchPolicy` and `pollRoundRobinLocked`; `internal/coordinator/service.go`, `NewService` (does not initialise `assignment`).
- Scenario: `NewService(...)`, then `SetDispatchPolicy("round_robin")` without `SetAssignmentSettings`. `s.assignment` is the zero value: `MaxLapses` 0 makes `j.AssignmentLapses >= 0` true for every job, so every poll claims the FIFO head by the lapse arm, and `BatchLimit` 0 makes the pass break before reading a candidate. One worker `w_1` (echo), one echo job, one poll gives `policy=round_robin_fallback fallback_reason=lapses` where ADR-0017 Section 3.2 expects an own-reservation claim. With `Interval` 0, every poll also runs a pass.
- Evidence (executed): `TestAudit_Probe_RoundRobinWithoutSettings` (proposed test) fails on `46ca30a`: `round_robin without settings claimed under policy="round_robin_fallback" reason="lapses"` (`probes-clean.log`).
- Why major, not blocker: the 5a binary never selects round_robin (handoff, known gaps). But fix round 1 added a configuration-time guard for the repository and not for the settings, and the 5c wiring in `cmd/coordinator/main.go` can hit this through a call-order mistake, with no error and no log.
- Suggested fix: initialise `assignment: DefaultAssignmentSettings()` in `NewService`, and have `SetAssignmentSettings` (or `SetDispatchPolicy("round_robin")`) reject settings outside the Section 5.5 ranges with `domain.ErrInvalidRequest`. Keep the probe as the regression test.

### F-5a-2 (minor): the claim's capacity guard has no test
- Location: `internal/storage/inmemory_assignment.go`, `ClaimForPoll` (`computeAvailableSlotsLocked ... ErrWorkerNoCapacity`).
- Scenario: a one-slot worker with a RUNNING attempt polls again while a job at the lapse limit is queued. With the guard removed, it claims a second job and runs two attempts on one slot. ADR-0017 Section 2.2 names this as "the real capacity check the claim also applies".
- Evidence (executed): A11 SURVIVED (84 PASS). `TestAudit_Probe_ClaimRespectsCapacity` (proposed test) passes on the tree and kills A11 (P11).
- Suggested fix: add the probe as a conformance test. SEC-005 asks for a mutation proof for each new guard.

### F-5a-3 (minor): the lapse-limit boundaries (implementation note 1 and L-1) are untested
- Location: `internal/storage/inmemory_assignment.go`, `AssignQueuedJobs` (candidate filter) and `ClaimForPoll` (lapse arm).
- Scenario A05: with `job_limit` at L lapses and `job_fresh` at 0 of the same type, the type stays in the pass, so the `<=` mutation reserves `job_limit` again, contrary to implementation note 1 (D9). The existing tests miss it: `TestConformance_AssignmentLapse_FallbackAfterLimit` leaves no fresh worker at the last lapse, and the PolicyField lapses case has a single job, so the type-list filter masks the candidate filter.
- Scenario A07: a job at L-1 lapses would be lapse-claimable one lapse early, and no test asserts a 204 at L-1.
- Evidence (executed): A05 and A07 SURVIVED. Probes P05 and P07 kill them.
- Suggested fix: adopt both probes.

### F-5a-13 (minor): the staleness check mixes the coordinator clock with the repository clock
- Location: `refreshIfStaleLocked` (`now := s.clock.Now()` against `ar.AssignmentPassState`, which is repository time).
- Scenario (inferred): in memory both clocks are the same real clock in production, and tests inject the same mock into both. In 5b, `last_completed_at` is database time. A coordinator clock 3 s behind the database makes `now.Sub(last)` stay at or below 2 s for a heartbeat that is in fact 5 s old, so refresh, and with it the age arm, is delayed by the skew. ADR-0017 assumes database time for the assignment clocks (Limits, ADR 0011 Section 5 item 5).
- Evidence: confirmed by code reading. `storage.Repository` already has `Now(ctx)`.
- Suggested fix: compare against `repo.Now(ctx)` (one read per stale-check) before 5b. Keep the process clock only for the rate limit, as Section 3.2 says.
