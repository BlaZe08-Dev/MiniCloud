## Findings

- **F-R1, minor, executed (`audit-mutants/audit-I4-red.log`).** Location: `internal/worker/poll_timing_test.go`, `relation` subtest. The test pins only `floor > MaxPollBackoff`. A backoff of 4.999 s (1 ms of margin) passes. Fix: Q1 (below).
- **F-R2, minor, executed (`audit-mutants/audit-M2-red.log`, 149 PASS).** The precedence between the lapse and age arms is not pinned on either backend. A memory backend that reports `age` when both arms qualify passes every test in storage, api and coordinator. Fix: Q3 (below).
- **F-R3, minor, confirmed by code reading.** `HandleSubmitJob` writes the `domain.Job` that `SubmitJob` returns (`internal/api/handlers.go:220`), so the 201 body carries the four fields. ADR Section 5.1 lists `POST /v1/jobs` as "No change". No test pins the 201 body. Fix: Q2 (below).
- **F-R4, minor, executed (`audit-M3`, `audit-M3p`).** The poll loop now waits on `realClock`, and no test exercises `realClock`. Halving every production timer passes all 38 worker tests; only the audit probe catches it. Fix: add a short real-clock test, for example the audit probe (about 3.5 s), or a unit test that `realClock.NewTimer(d)` does not fire before `d`.
- **F-R5 (F-5c2-1 confirmed), major, executed, pre-existing on main.** `audit-probe-backoff-tip.log` shows `ComputeBackoffWithJitter` returns 0 s at 64, 65, 100 and 1000 failures for the poll (200 ms / 3 s), renewal (1 s / 10 s) and delivery (200 ms / 5 s) parameters. At 64 the shift gives `1<<63` (negative) and the product overflows to 0; from 65 the shift itself gives 0.
  - Minimal fix: clamp the count before the shift, `if failureCount > 5 { failureCount = 5 }`, since 1<<4 = 16 is the multiplier cap. Diff: `audit-fix-F-5c2-1.diff`. With it, every draw from 5 to 1000 failures stays in [cap/2, cap) (`audit-probe-backoff-fixed.log`), and `./internal/worker/` passes (`audit-fix-worker-pkg.log`). Both were executed in the throwaway worktree only.
  - Exposed callers:
    - `Agent.Run`, both error arms (`client.go:197`, `client.go:202`). The failure counter is unbounded, so the bug is reached after 64 failed polls (confirmed by code reading).
    - `renewLoop` (`client.go:549`). Its counter is unbounded while renewals stay transient, and the wait becomes `min(0, interval)` = 0. That is reachable for a long task during an outage: roughly 30 s to 5 min of failures, for an interval of 1 s to 10 s (inferred).
    - `deliverResult` (`client.go:716`) is **not** reachable inside `ResultDeliveryBudget` (60 s). The minimum sum of the first 63 backoffs is 0.1 + 0.2 + 0.4 + 0.8 + 59 x 1.6 = 95.9 s, more than 60 s (confirmed by code reading).

## Orchestrator decisions (judged)

- **Q1 (margin of at least 1 s): agree, with conditions.** The ADR gives no number, and the 15 s poll HTTP timeout means no floor of 15 s or less can cover a worst-case round trip. So the margin is a policy choice and not a proof, and 1 s is reasonable (current slack: 2 s). The number must be recorded in ADR Section 3.1 or INV-17 (the design doc wins), and it must be a named value in the test. After the change, `audit-I4` must be killed.
- **Q2 (201 keeps the four fields): agree.** At submit time the fields are always null, null, 0 and null, so they expose nothing. Record the decision in ADR Section 5.1 and `docs/protocol.md` as an amendment, not only as a deviation note. The test should assert that the four keys are present with those values and that `assigned_at` is absent.
- **Q3 (pin `lapses` when both arms qualify): agree.** The ADR lists arm (a) first, but it does not order the arms, so "not ADR-mandated" is accurate. Add a shared case that both backends run under the same name: one job with lapses at or above `L` that is also aged, with the pass silent and the age arm open, expecting `lapses`. `audit-M2` must then be killed, and so must its PostgreSQL twin, `byLapses && !opts.AgeArmOpen` in `postgres/assignment.go` (designed, not executed).
- **Q4 (F-5c2-1 goes to P4-14): agree.** The bug is pre-existing and the fix touches a function shared by three loops. Two conditions: P4-14 must cover the renewal path (F-R5), and once it lands, `TestPollTiming_RunSleepsWithinMaxBackoff` should add the lower bound (sleep of at least `MaxPollBackoff/2` in the capped region). Today the test tolerates 0 s sleeps.
